> 状态：**🟢 搁置（无实施计划）**

## 原始需求

设计 i18n 国际化基础架构，支持多语言界面切换。

审计报告原文：
> "多语言支持：i18n 框架（当前仅中文界面）"

## 搁置理由

### 1. 无实际需求

- **单一中文用户**：项目为个人工具，用户界面仅中文
- **无多语言场景**：无国际化部署、无海外用户、无多语言内容源
- **内容本身是中文**：采集的情报源（微博/知乎/B站/公众号）均为中文，英文内容通过翻译功能处理

### 2. 实施成本极高

| 工作项 | 估算工作量 |
|--------|-----------|
| 抽取全部 UI 字符串（前端 38 组件 + 管理后台） | 2-3 人天 |
| 引入 i18n 框架（react-intl / next-intl / i18next） | 0.5 人天 |
| 创建 locale 文件（zh-CN / en-US 至少） | 1 人天 |
| 翻译全部内容（数百处 UI 字符串） | 2-3 人天 |
| 后端消息/日志国际化 | 1 人天 |
| 测试 + 回归 | 1 人天 |
| **总计** | **7-9 人天** |

### 3. 收益为零

- 无多语言用户，英文界面无人使用
- 维护两套 locale 文件增加日常开发负担
- 新增功能时需同步更新两套翻译，拖慢迭代速度

### 4. 当前已有替代方案

- **AI 翻译功能**：`server/services/ai/enrich.js` 对英文内容自动翻译摘要
- **双语详情**：`HotDetail.jsx` 支持中英文对照显示
- **内容层国际化**：采集的英文源自动翻译，无需 UI 国际化

## 未来启动指引

如项目演进到以下阶段，可重新评估：

1. **多用户/团队使用**：有非中文用户时
2. **开源发布**：面向国际开发者社区时
3. **多语言内容源**：需要英文/日文等界面匹配内容语言时

启动步骤：
1. 选型：推荐 `react-intl`（React 生态成熟）或 `next-intl`（如迁移到 Next.js）
2. 抽取：使用 `formatjs extract` 自动扫描 JSX 中的字符串字面量
3. 创建 `web/src/locales/zh-CN.json` 和 `en-US.json`
4. 包裹 `<IntlProvider>` 到 `main.jsx`
5. 逐组件替换硬编码字符串为 `<FormattedMessage>` 或 `useIntl().formatMessage()`

## 简化替代方案

如仅需英文界面（而非完整 i18n），可：
1. 创建 `web/src/i18n.js` 简单键值映射
2. 用 `localStorage` 存储用户语言偏好
3. 只翻译导航/按钮/标签等高频 UI，其余保持中文
