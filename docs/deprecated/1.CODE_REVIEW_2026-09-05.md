## 一、系统全景（核实后）

本机即生产机的全网情报聚合系统，当前处于「本地全功能 + 云端冻结」过渡形态：

- **本地主系统**（:3000，Express + better-sqlite3/WAL）：采集调度器 + SQLite 任务队列 + 阅读器/日报/热榜三页面 + `/admin/` 管理台。目标部署形态为宝塔 + PM2（`ecosystem.config.js` 已就绪：fork 单实例、512M 内存重启、指数退避）。
- **云端 portal**（Vercel + Turso，**冻结态**）：单 serverless catch-all 函数 `portal/api/[...slug].js` 承接全部 `/api/*`；Turso 优先 + `public/data/*.json` 静态快照兜底。语义漂移（日报候选类型、熔断计数位置、热榜 score 等）已确认存在且属有意不修。
- **公众号**：we-mp-rss 退役痕迹在本地已清理干净；375 个 wechat2rss 源以 `type='rss'` 导入，全文走 `content:encoded`。portal 端 `_collect.fetchWemp`、`_admin` 微信读书扫码、src-admin WereadTab 残留，属冻结态容忍的腐化。

## 二、核心机制（代码核实）

### 采集主链
调度器每 60s `scanAndEnqueue`（ticking 防重入）→ `job_queue` 入队（focus 源优先级 100）→ TaskQueue 每 2s 消费（并发 5、同源 running 限 1、启动 running→pending 崩溃恢复）→ `fetchSource`（withSourceLock 同源互斥）→ 适配器抓取 → `INSERT OR IGNORE` by url 落库 → 更新 `next_fetch_at` / 清 `fail_count`。失败 → `fail_count+1`，≥3 自动熔断 `enabled=0`，≥2 异步触发报警。解冻唯一入口 `store.unfreezeSource()`。`QUEUE_ENABLED=false` 回退串行。

### 适配器要点
- 契约校验宽松（仅 type/fetch/match）；注册顺序 bilibili→wechat→douyin→x→hotlist→rss（rss 兜底）。
- **rss**：条件请求 304、`customFields:['content:encoded','content']`、GBK/Big5 charset 嗅探、`data-src→src`、mmbiz 加 `no-referrer`、垃圾内容判弃、全文补抓 60s 总预算限最新 10 条；YouTube 频道自动转 videos.xml。
- **hotlist**：`hotlist://{id}` 规范、newsnow API、热度归一（万/亿）、乱码摘要丢弃、60s 源 `日期#序号` 构造稳定 URL。
- **bilibili**：wbi 签名（密钥缓存 30min、-403/-799 强刷重试一次）、主链 `arc/search` + 兜底 A 合集（≤5 页）+ 兜底 B 搜索；-352/412 风控走兜底；Cookie 优先 credentials 表，无则匿名 buvid（缓存 1h）。
- **douyin**：Playwright + storageState；全局串行队列任意两次主页访问 ≥10s，限速时间戳持久化 settings 重启不破坏；三级视频提取（接口响应→SSR RENDER_DATA→递归 aweme_id）；扫码登录有头浏览器 5min 超时。

### 日报引擎
48h 窗口候选（wechat/rss/x + bilibili/douyin/youtube 视频）→ focus 全收 + 关键词栏目分类 → Jaccard≥0.5 同主题合并（一手源优先）+ 同源限流 ≤3 → 出库安检（`hasMojibake`/`isErrorPageItem` 剔除）→ 破茧栏（events 域外 Top5）→ 落 `daily_reports`。启动时 `needsGeneration()` 补跑。

### 事件聚合 / 报警 / 队列
- events：仅 articles 表 72h 窗口，Jaccard≥0.4 聚类，热度 = Σ(1+min(1,score/1e6)) × 0.5^(ageH/24) × 1.5^(信源数-1)，纯内存 5min 缓存。
- alerts：7 渠道（钉钉/企微/飞书/Server酱/Bark/TG/webhook，HMAC-SHA256 加签），冷却存 `settings['alerts.cooldowns']`，网络失败时 undici 直连重试一次。
- poller：云端 PHP 队列（wechat/bilibili/douyin）pull→pending_items→resolve→clear。

抽查 A1/A2/A3/A5/A7/A8/A11/A12 等修复点，全部在当前代码中有精确落点且语义一致；报告自述测试计数（21 回归/20 冒烟/19 云端探针）与实际精确吻合。**该报告可信。**（当前测试总数实为 125 项，文档中"107 项"已过时。）

### 设计张力（需决策，非 bug）

- ARCHITECTURE 称「调度器串行是有意的（抖音/B站并发会被秒封）」，但队列并发 5 下**多个 B站源会真正并发**——抖音靠适配器内全局串行队列兜底，B站只有同源锁，跨源无限速。
- `hot.js query()` 无 SQL LIMIT，聚合源文章全量进内存过滤；`queue/pending` 无 LIMIT。
- 错误响应约定不统一：daily/regenerate、hot.js 失败返回 HTTP 200 + `{ok:false}`，sources/refresh 用 500。
- `runPortalSync` 用 execSync 跑 vercel build/deploy，阻塞事件循环数分钟（2h 一次）。

## 四、总体评价

工程质量在本人类项目中属上乘：参数化查询无注入面、熔断/解冻/安检语义收敛到唯一入口、图片代理有完整 SSRF 防护链（DNS 逐 IP/IPv4-mapped/重定向逐跳/15MB 流式）、125 项测试含"防回归的回归"元测试、已知坑有注释传承。

核心风险高度集中：**当前系统实质是无鉴权的局域网应用**（P0-1），按部署决策搬上宝塔公网前，鉴权链路是第一优先级。其次是会持续产生实际损害的逻辑缺陷（P1-1 越权抓取、P1-3 job_queue 膨胀）。
