## T3-1 早报体系 v3：每日早报（公共版）+ 我的早报（个性化）

**统一约定**

- **生成窗口**：两报都改为晚间生成，窗口 =「前一天 00:00 ~ 当天生成时刻」，做"晚间整理，读前一天 + 白天"的自然日回顾；夜间另留一档备跑兜底。具体时刻只写在作业文件里。
- **配额优先级**：**早报/周刊生成 > 翻译**。生成窗口前后若干小时内，翻译批次自动缩小上限（可为 0），窗口外恢复。
- **主题全景**：两类早报都新增「主题全景」区——把当日高评分碎片按主题聚类（跨源相似 + AI 命名），每个主题给四类视角标签（事件 / 领域 / 人物 / 产品对比），并附一段不超过百来字的主题综述。

**每日早报（公共版）**

- 来源范围 = 全部启用源；为空时取全量。管理台要能勾选。
- 高评分内容正常入选；另设**破茧位**：混入未订阅/低频源的高分内容并打「探索」标记。
- 六维评分（选题/内容/深度/实用/创新/表达）在条目内联展示评分与理由。
- 增设「补充阅读」栏，固定条数（与我的早报同一口径）。

**我的早报（个性化）**

- 订阅集合 + 行为加权：由阅读行为算出的兴趣画像影响排序权重（画像本身不可配，见 ADR-23）；每个兴趣域可配条数上限。
- 条目形态：摘要 + 关键观点 + 金句，按主题分组呈现；补充阅读取非订阅源高分内容并标注来源。
- 每日生成一份「阅读小结」回顾页：当日已读篇数、时长分布、收藏/稍后读、头部来源，附一句总结。

**周刊**

- 每周生成时附一段 AI 周总结（本周主线/趋势判断），显示在页脚注，归档条目同步保存。

**什么算做完**：两报在晚间窗口自动生成且覆盖窗口正确、推送含主题全景；生成窗口内翻译确实让路（日志可见）；每日早报有探索位与补充阅读；我的早报条目有摘要/观点/金句、主题全景四视角可见；周刊有 AI 周总结；阅读小结与当日真实记录一致。

## T3-2 管理台「早报中心」+ 后台体验整改

**背景**：早报/我的早报/周刊已上前台，但后台没有对应管理页；且后台信息架构被用户判为"看着不合理、只有源库可用"。

- **早报中心**：每日早报（来源勾选 / 栏目管理 / 生成时间 / 破茧与探索位开关 / 手动重新生成）；我的早报（订阅源选择器 / 域配额 / 推送开关 / 画像查看）；周刊（生成时间 / 归档列表管理 / AI 总结开关）；生成历史（近 7 天一览：成功 / 降级 / 耗时）。
- **体验整改**：监控折线（前提是心跳改成追加式数组，不再只留当前值）、数据饼图、报警时间线。
- **云端写端点**：三类报的设置都要有写通路，先校验后写入并留审计。

**什么算做完**：云端后台能完成上述配置并真生效；生成历史如实反映批次结果；移动端可用。

## T3-3 读层性能

**动手前先重测**：历史耗时读数取自已废弃的旧库，不能当现行基线；要优化就按 `docs/DELIVERY_VERIFICATION.md` 现测一遍再定。

- 阅读列表：把"计数"和"条目"拆开，首屏只要条目 + 粗计数；聚合走覆盖索引；沿用游标分页。
- 状态概览：拆成轻量核心（未读 / 今日新增，一次索引计数）+ 慢速榜（来源榜、入报统计，前端懒加载独立端点）。
- 热榜：补按分数与发布时间排序的索引。
- 前端：页面级短缓存 + 骨架屏替代"加载中"，并对相邻页做预取。

**什么算做完**：三个慢接口线上实测 P95 达标；切换页面不再出现几秒空白。

## T3-6 B 站采集方案调研

现状是匿名降级覆盖大部分场景，配 Cookie 可解锁主链但有风控风险。要调研：把登录态注入 runner 的稳定性、官方开放平台或替代源、结论先落档再实施。**约束**：runner 依赖面只许纯 JS（ADR-21），所以"在 runner 上跑无头浏览器"这类方案不在候选里（ADR-02）。

## T3-7 对边界轮存续项（需求定义与边界，非排期）

### 一、四个目标必须同时成立

见 **ADR-24 · 策展四目标不可拆**。这一节不再自带因果链——决策住在决策件里，写在这里会和那份各自过期。
下面第二、三节是**这四个目标当前在哪一级没成立**的清点，属需求定义，不是决策。

### 二、零额度预筛五级阶梯：本系统每一级的实情

| 级 | 现状 | 这条边界是什么 |
|---|---|---|
| 1 地址精确去重 | **在本系统冗余**：地址唯一性在入库那层就挡住了 | 别再为它建一级流水线 |
| 2 正文指纹近重复合并 | 未实现。**成本不在算法在取数**——候选查询故意不带全文（一次拉几天几千行全文会被数据供应商掐断） | 做它必须先回答"正文怎么单独取、一次取多少" |
| 3 每源预配额 | 已接进生产链路（默认值读实现；写端点已通，界面格与人工保存验证还欠着，账在 `docs/ISSUES.md` 观察中——"键可写"不等于"人可配"） | 只换覆盖宽度，**不改进报门槛**；别当质量闸（ADR-09） |
| 4 规则过滤（标题党词表 / 通稿特征） | **位置放错**：这套词表现在交给模型判 | 正是"用美元做正则能做的事"，该下沉成零额度规则 |
| 5 主题分组 + 边缘桶 | **完全没有**。现在的栏目是事后关键词匹配，不是事前分组 | 不做这级，"边缘文章不消耗日常额度"这句话就不成立 |

**这一层唯一被实验支持的形态**：统计学的筛法只能当**兜底排序 + 只砍最底一段**（池子超配额时优先牺牲最低分那一小段），不能当质量闸；规则类判据先上。回测口径、压缩比与"为什么当门槛站不住"都在 `docs/eval/2026-09-24-prescreen-labels.md`，收紧工作点还欠一批人工标注（账在 `docs/ISSUES.md`「等你操作」）。

### 三、分配层有三处与设计参考**方向相反**（尚未开讨论）

- **源先验分实际在决定入场**：它被直接乘进总分，而"够不够格进报"发生在加权之后——小源乘完更易跌破门槛。参考文档明写先验分只影响组内排序。现在的方向是**放大马太效应**。
- **低曝光保护位由评分填充**：保护位条件是"近 14 天未入报**且**分数达标"。参考文档点名这是反模式——探索位不由评分填充，否则只是评分系统给自己找替罪羊。
- **下游阀门管不住上游漏斗**：单源单日入报上限确实存在，但它保护的是版面；挤压发生在候选池。别把这两个当同一件事、以为已经解决。

### 四、四类视角不是从零做

主题全景的"视角"现状就是事件 / 领域 / 人物 / 产品对比四类（页面上能看到标签）。缺的是把"标签"升级成"权重模板"——同一篇文章在不同槽位得分不同，避免深度长文和快讯在同一池子比总分。

### 五、一条纪律建议（未落地，且会反复咬人）

设计参考的纪律清单全是"该做什么"，**没有一条是"做不成时我怎么知道"**。初筛那次间歇性失效证明最先坏的正是这里：它报"候选 500 / 通过 500 / 剔除 0"，与"模型真的认为这 500 篇全都值得深析"在数据上**完全同形、不可判别**。

建议补一条通用纪律：**每一级预筛/筛除都要有可判别的自证输出**（调用数、失败数、削减数）；削减数为 0 或失败率超阈值时判"环境失败"而不是判"没问题"。不加，上面第 4、5 两级每落地一级都会以同样方式再坏一次。

### 六、用户页面标注里仍未处置的

**每日早报页**

1. **缺按期回看**：期号和几十期历史都在库里，但每日早报没有"历史索引"端点——周刊和我的早报都有，唯独它没有。数据在、入口缺。
2. **栏目名不该来自固定关键词表**：现在五栏全来自后台关键词表，AI 主题只是额外多出来的一块，两者并存。栏目名应根据当天内容决定。
3. **排版要按 3 的倍数填满**：一栏只放一条很难看。
4. **两三星条目大量进报**：抽查那一期 65% 的条目 ≤3 星。成因不是模型放水，是**进报分数门槛换算成星级后恰好落在 2 星**——门槛和星级是两套刻度，从来没人对过。
5. **视频/播客标题没翻译、缺摘要、播客配图有问题**（可只放图片，像视频那样）。根因不是漏跑一次翻译，是**视频这张表没有承载译文的字段**。修它要动表结构 + 三端一致 + 翻译管线接线，不是一次跑批。
6. **排序下拉与高亮不是死控件**，两个都真的生效——这是**可发现性问题**（没有任何提示）。修法是加说明或改交互，不是"去把它接上线"。
7. **"候选内容 500"名不副实**：它不是写死的常量，但它和旁边"公众号文章 500"读的是同一个数，两张卡显示同一个值。

**管理后台**

1. 功能隔离：所有板块放页面**最左侧**；每个功能都要有确实的作用；方便使用，不要太复杂。
2. 系统需要**自愈能力**：有的源超过一定时间/次数自己就断了，源本身没问题，每次都要人或 agent 去点开。用户注明"手法有待商榷，在考虑是否用任务队列"。
3. 新加**日志板块**：作业日志 + 源熔断日志 + 服务器错误日志 + 部署失败 + 数据层失败日志。
4. **拆开繁重的板块**：源库里既塞每日早报又塞源管理；早报中心既有多份报又有周报，有的功能冗长一大块。**提示应做成"帮助"或功能名旁的圆圈问号悬浮显示**，而不是功能没做却先摆一段 tips。逐项点名：早报历史改了不显示、周刊归档太薄、我的早报设置功能少且不明所以、画像感觉没生效、生成时间与手动触发不可调节（像 tips 不像功能）、每日早报设置不实用、项目管理是老版本残留、热点榜策展在新版上不明所以。
5. **AI 能力**：供应商改成**下拉菜单**可切模型；有官方 API 的填进接口/密钥/地址后**自动列出该 API 支持的模型**；模型旁**直接能测延迟**，用红黄绿表示强弱；这块功能太少——系统里 AI 负责很多管线，这里既加载不了也看不到控制。
6. 功能块拆开：报警、日志、监控各归各。
7. **主页**：健康概览与源抓取成功率适合当进后台首屏，但只有两张太单薄，要补内容。
8. 逐项点名：健康概览要有跳转、要有功能；任务队列没功能也不知道有什么用；源抓取成功率没功能、只知道失败、操作复杂、还只覆盖部分源；报警管理模块太少，且**有的模块根本没在报警**。

### 七、这批标注里有一处要用户自澄清

第 2 项想把"源自愈"**做成任务队列**，第 8 项又判**任务队列没功能、不知道有什么用**。同一个机制既被提议当载体又被判无用。要先问清：是"砍掉现有队列面板、队列作为自愈载体保留"，还是"自愈换别的实现"？

### 八、取证口径的一条硬提醒

**别拿"日入库量"当"日报候选池"的分母**：入库量里有大量滞后回填的旧文（有的发布上百天才入库），而日报窗口按发布时间过滤——那些旧文根本不在窗口内。用入库量算覆盖率会低一个数量级，进而把"候选池太小"整个判错。其余同类口径坑（时间串格式不一致导致系统性偏新、窗口参数单位是小时不是天）见 `docs/pitfalls/`。

## T4-3 内容形态补全

- **视频/播客入报**：视频与播客有更新时纳入三类报的候选（现在的候选类型只含文章类）；早报条目带类型徽章，视频不进阅读器文章流（独立区块）。
- **小宇宙桥接调研**：两个无官方 RSS 的节目要找第三方桥或放弃。
- **替代公众号源**：某个聚合站的六个公众号需要一次人工订阅激活才能出 feed，拿到 URL 后入库，用来补已退役的那批源。

## 优化方向（源与数据治理，未排期）

1. **先挡系统性故障**：一次代理故障会让全库源同时失败并被逐个计入熔断，这是当前唯一能一次性打瘫全库的缺陷。要一条判据——但**必须过坑 #39 的三闸门**（量级 + 同源性 + 环境类），只看"失败率高/错误长得像"的朴素修法会把真死源集体赦免（坑 #39 论证过为什么错）。（账在 `docs/ISSUES.md` H16）
2. **本地端补自动恢复**：纯增量，不动云端语义；顺带把历史上被锁死的一批源按类别分批试探恢复。（H14 / H15）
3. **退避按错误类别分级 + 解冻前先探活**：把"一刀切长时间流放"换成分钟级退避；**判定为解析器缺陷的一律不熔断**——那是我们的 bug，锁源等于把问题藏起来。
4. **界面收敛**：抓取成功率、健康概览、报警、日志、监控各自成块，别再互相塞。
5. **早报体感尾巴**：本期索引、页签切换卡顿、门槛跑批验证等零散项，逐条回 `docs/ISSUES.md` 看现状。
6. **后台大重构放最后**（默认最低优先级）：等上面这些行为与数据语义稳定后再动布局，且必须先出总规格、逐板块批准，再动代码。
7. **库体积治理**（ISSUES H26）：正文迁出主表 / 入库前压缩 / 归档窗口作配角 / 搜索不扫正文列，均需立规格；"上全文索引"与 ADR-20 相抵，动前先过那条 ADR 的重开判据。
