## T3-1 早报体系 v3：每日早报（公共版）+ 我的早报（个性化）

**统一约定**

- **生成窗口**：两报都改为晚间生成，窗口 =「前一天 00:00 ~ 当天生成时刻」，做"晚间整理，读前一天 + 白天"的自然日回顾；夜间另留一档备跑兜底。具体时刻只写在作业文件里。
- **配额优先级**：**早报/周刊生成 > 翻译**。生成窗口前后若干小时内，翻译批次自动缩小上限（可为 0），窗口外恢复。
- **主题全景**：两类早报都新增「主题全景」区——把当日高评分碎片按主题聚类（跨源相似 + AI 命名），每个主题给四类视角标签（事件 / 领域 / 人物 / 产品对比），并附一段不超过百来字的主题综述。

**每日早报（公共版）**

- 来源范围 = 全部启用源；为空时取全量。管理台要能勾选。
- 高评分内容正常入选；另设**破茧位**：混入未订阅/低频源的高分内容并打「探索」标记。
- 六维评分（选题/内容/深度/实用/创新/表达）在条目内联展示评分与理由。
- 增设「补充阅读」栏，固定条数（与我的早报同一口径）。

**我的早报（个性化）**

- 订阅集合 + 行为加权：由阅读行为算出的兴趣画像影响排序权重（画像本身不可配，见 ADR-23）；每个兴趣域可配条数上限。
- 条目形态：摘要 + 关键观点 + 金句，按主题分组呈现；补充阅读取非订阅源高分内容并标注来源。
- 每日生成一份「阅读小结」回顾页：当日已读篇数、时长分布、收藏/稍后读、头部来源，附一句总结。

**周刊**

- 每周生成时附一段 AI 周总结（本周主线/趋势判断），显示在页脚注，归档条目同步保存。

**什么算做完**：两报在晚间窗口自动生成且覆盖窗口正确、推送含主题全景；生成窗口内翻译确实让路（日志可见）；每日早报有探索位与补充阅读；我的早报条目有摘要/观点/金句、主题全景四视角可见；周刊有 AI 周总结；阅读小结与当日真实记录一致。

## T3-7 对边界轮存续项（需求定义与边界，非排期）

### 一、四个目标必须同时成立

见 **ADR-24 · 策展四目标不可拆**。这一节不再自带因果链——决策住在决策件里，写在这里会和那份各自过期。
下面第二、三节是**这四个目标当前在哪一级没成立**的清点，属需求定义，不是决策。

### 二、零额度预筛五级阶梯：本系统每一级的实情

| 级 | 现状 | 这条边界是什么 |
|---|---|---|
| 1 地址精确去重 | **在本系统冗余**：地址唯一性在入库那层就挡住了 | 别再为它建一级流水线 |
| 2 正文指纹近重复合并 | 未实现。**成本不在算法在取数**——候选查询故意不带全文（一次拉几天几千行全文会被数据供应商掐断） | 做它必须先回答"正文怎么单独取、一次取多少" |
| 3 每源预配额 | 已接进生产链路（默认值读实现；写端点已通，界面格与人工保存验证还欠着，账在 `docs/ISSUES.md` 观察中——"键可写"不等于"人可配"） | 只换覆盖宽度，**不改进报门槛**；别当质量闸（ADR-09） |
| 4 规则过滤（标题党词表 / 通稿特征） | **位置放错**：这套词表现在交给模型判 | 正是"用美元做正则能做的事"，该下沉成零额度规则 |
| 5 主题分组 + 边缘桶 | **完全没有**。现在的栏目是事后关键词匹配，不是事前分组 | 不做这级，"边缘文章不消耗日常额度"这句话就不成立 |

**这一层唯一被实验支持的形态**：统计学的筛法只能当**兜底排序 + 只砍最底一段**（池子超配额时优先牺牲最低分那一小段），不能当质量闸；规则类判据先上。回测口径、压缩比与"为什么当门槛站不住"都在 `docs/eval/2026-09-24-prescreen-labels.md`，收紧工作点还欠一批人工标注（账在 `docs/ISSUES.md`「等你操作」）。

### 三、分配层有三处与设计参考**方向相反**（尚未开讨论）

- **源先验分实际在决定入场**：它被直接乘进总分，而"够不够格进报"发生在加权之后——小源乘完更易跌破门槛。参考文档明写先验分只影响组内排序。现在的方向是**放大马太效应**。
- **低曝光保护位由评分填充**：保护位条件是"一段时间未入报（窗口取值读实现）**且**分数达标"。参考文档点名这是反模式——探索位不由评分填充，否则只是评分系统给自己找替罪羊。
- **下游阀门管不住上游漏斗**：单源单日入报上限确实存在，但它保护的是版面；挤压发生在候选池。别把这两个当同一件事、以为已经解决。

### 四、四类视角不是从零做

主题全景的"视角"现状就是事件 / 领域 / 人物 / 产品对比四类（页面上能看到标签）。缺的是把"标签"升级成"权重模板"——同一篇文章在不同槽位得分不同，避免深度长文和快讯在同一池子比总分。

### 五、一条纪律建议（未落地，且会反复咬人）

设计参考的纪律清单全是"该做什么"，**没有一条是"做不成时我怎么知道"**。初筛那次间歇性失效证明最先坏的正是这里：它报"候选 500 / 通过 500 / 剔除 0"，与"模型真的认为这 500 篇全都值得深析"在数据上**完全同形、不可判别**。

建议补一条通用纪律：**每一级预筛/筛除都要有可判别的自证输出**（调用数、失败数、削减数）；削减数为 0 或失败率超阈值时判"环境失败"而不是判"没问题"。不加，上面第 4、5 两级每落地一级都会以同样方式再坏一次。

### 八、取证口径的一条硬提醒

**别拿"日入库量"当"日报候选池"的分母**：入库量里有大量滞后回填的旧文（有的发布上百天才入库），而日报窗口按发布时间过滤——那些旧文根本不在窗口内。用入库量算覆盖率会低一个数量级，进而把"候选池太小"整个判错。其余同类口径坑（时间串格式不一致导致系统性偏新、窗口参数单位是小时不是天）见 `docs/pitfalls/`。

## T6 10-08 计划轮（用户点单立七条，本轮不开发、不测试、不修复）

### T6-1 自愈补全（本文件内的自愈欠账只写在这一条）

**判据与规则不在这里复述**：自愈该做成什么样，承载处是坑 #35 的规则清单①–⑤（含"三端同一份实现落 `lib/`"那条硬要求），系统性故障抑制的三闸门在坑 #39。本条只记**现在有哪几件没落地**：

- **本地端没有"按时间自动恢复"那条线**：恢复入口全是手动，而且散在多处（源表 / 健康页 / 一键恢复 / 源库那几处都有，H14 里"两个人工入口"的计数不准）。唯一的例外是公众号 OPML 同步附带的一处自动解冻——它不是按时间自愈，**别把它当成"本地已经有恢复线"**从而把本条判成已做。
- **冷却不分错误性质**：我方解析缺陷与真死源走同一条 `fail_count` 判据（#35 根因③ / 规则②未落地）。
- **解冻前不探活**：放回即撞同一次故障、把冷却窗烧光（#35 规则③未落地）。
- **本地那批历史锁死源还没按类别试探恢复**——云端那批已按坑 #76 的分批 + 备份 + 探针判活跑完并复验（H15），本条不与它抢账；本地存量读数见 #35 ④，那份标注"未复测"，动手前先现读一次再定批次划分。

**什么算做完**：三端自愈走 `lib/` 同一份实现（不许各写一遍）；解析器缺陷不再计入熔断；每次恢复/降频留痕、后台可读、恢复后不回升；本地锁死源按类别分批试探完，留下"活回/仍死"的分拣读数。

### T6-2 早报产出归因：每期"少了什么、为什么少"必须可判别

**现象**：10.8 早报只有部分内容，后台只答得出"是不是关键词档"这一个比特。四条独立成因都能长成"内容少"这一个形态：入报门槛削减（ADR-37 明写高分不足时栏目允许变短甚至为空、宁缺毋滥；门槛取值读实现，不在这里背数）、初筛与深析两段的批次预算截断、版面限流（单源与全局各有条数上限）、深析连败真降级。

**但"四条全分不出"是说过头了——账已经有一半**：期级产出里现在就能现读**进门槛前的候选数**、**门槛剔掉的条数**、**初筛段有没有被预算截断**（这几项按写入器注释要求多端同口径）。所以本条不是从零建归因，缺的是另外两段计数、深析段的失败分类，以及把这些散数拼成一条链的那一处视图。

**这条要的不是修 10.8，是把缺的那半补上**，形态沿用 T3-7 第五节那条通用纪律（每一级筛除都要有可判别的自证输出；削减数为 0 或失败率超阈值时判"环境失败"而不是判"没问题"）：

- **补两段计数**：深析段的预算截断（到点直接放弃剩余候选，现在不挂任何标）、版面限流剔掉的条数（上限生效时不计数）。
- **串成一处期级产出账**：候选数 → 门槛削减 → 初筛截断 → 深析截断 → 版面限流 → 实际入报。**这是读数拼装，不是新判据**，别为它再立一套口径。
- **深析失败按错误类别分档**：初筛段已经有一套按错误类别的归因并随失败原因落库（含限流那一类，见 H35），**深析段没有**——它对任何失败都只回一个空，于是"额度不够"与"代码报错"只在深析这一段同形。**分类必须沿用初筛那同一处定义，不许为深析另起一套**，否则就是第四份判据。
- **配额余量是另一件事**：用量侧已有按 provider 的分列与错误串，但"这一期还剩多少额度"读不出——那属 T6-3 的范围，不由本条交付。
- **禁止**：为填版面回退门槛或放宽限流（与 ADR-37 相抵，要动先动决策件）；在没有上面这套读数时把"内容少"归因给额度。额度是头号嫌疑而不是结论——坑 #A1 量过免费池的耗尽与自愈节律（取值不在此背）；**初筛段撞没撞限额已经读得出**（限流那一类归因就在里面），读不出的是**深析段**，那一段现在只能靠连续失败报警倒推。

**什么算做完**：任一期早报能在一处现读出上面那条链的每一段；深析失败有类别；后台"降级"那一处能说出这一期落在哪一档、由哪一类失败造成。

> 10.8 当期读数按 `docs/ISSUES.md` 观察中"入报门槛首战"那条给的现读法取，本轮按用户裁决不跑、不修；同一现象不在两张表各立一份账。

### T6-3 AI 产能：翻译与早报生成用多账号轮询保产能

**动机（用户 10-08）**：早报与翻译共用一条 AI 通道，通道产能是一期早报能不能出全的上游约束，希望用多账号轮询把产能撑住。

**10-13 已落地（用户拍板直接实施）**：账号池长在统一通道（`api/_ai.js`），配置源唯一（Turso `settings['ai'].apiKeys`，管理台「AI 配置 → 账号池」可改，env `AGNES_API_KEYS` 仅兜底）；额度耗尽（402/403/429 + 配额语义）自动登记 `ai.keyExhausted`（12h 探活）并轮切下一账号，整池耗尽明报错不静默减量；每账号调用量读数长在 `ai.stats` 的 byProvider（agnes#1/agnes#2 分列）；本地端同名 env 池 + 进程内轮切。**仍欠**：额度余量读数（供应商未暴露余量 API，只能从失败语义倒推）与"从第几篇开始撞限额"的期级归因（T6-2 的产出物）。

**仍受 T6-2 排序约束的部分**：额度可观测性没长全之前，池子解决的是"单账号耗尽拖死整批"，不解决"配额总量不够"——后者要靠覆盖目标的读数（T7-2）来判断。

### T6-4 前台阅读器正文布局（ISSUES 无对应条目，本条是唯一承载处）

用户 10-08 判定"所有前台阅读器正文布局还是有问题"。此前多轮排版整改没修干净，说明病在结构而不在个案：**正文有两种来源形态，而元素级的排版规则只覆盖其中一种**——纯文本那条分支缺的是段距、标题层级、列表、代码块这类，容器级的字号行高仍在，所以症状是"结构要素没有版式"，不是整片裸奔；**站外抓回的整页内容靠逐条反向抵消源站样式**；**正文取空或过薄时入库的仍是"看起来像一篇文章"的东西**。三处的具体实现位置指代码，不在这里复述。

**方向（要拍的取舍）**：版式由"我们要求的正向规则"决定，而不是给源站类名打补丁；无正文／薄正文要有自己明确的缺省形态，不伪装成一篇正常文章。

**边界**：不改阅读器入口与默认视图（ADR-29 钉的是入口形态）；正文重排不做 AI 改写（那是 T6-5）；样式层改动不许顺带改数据侧来源优先级——原文／译文／摘要谁优先属数据语义，要单独裁。**现存反例先认下来**：热点详情那处正文并没走这条渲染链，本条下文说"共用一条渲染链"时不许把它算成已经共用。

**什么算做完**：取一批真实问题样本（两种来源形态、薄正文、站外整页各若干）在真实前台逐条看：同一栏目内不同来源的段距、标题层级、图片、列表、代码块表现一致；薄正文不再呈现"打开只有一行"。

### T6-5 我的阅读：从"只给外链"到站内可消费

用户 10-08 说的"只能看原文"比表面更靠前一层：**"我的阅读"这一页点标题直接跳外链**，而站内其实已经有正文视图（阅读器页与早报那几处在用的正文渲染，速览卡连要点和金句都会渲染）——缺的不是"新做一套"，是这一页没接上。这条比原想象便宜。

但这几件事的份量并不一样，别打包成一个需求：

- **接站内正文视图**：复用 T6-4 那条渲染链，属页面接线；禁止在"我的阅读"里手写第二遍排版。
- **补投影**：分数／理由／译文**库里早有列**（深析会回写），是那个列表接口没把它们取出来——属接口投影改动，不动数据模型。
- **真缺的只有要点与金句**：它们只活在报告产物里，文章行上没有这两样。要做必须先拍"落哪几样进文章表"，**这是三件里唯一的数据模型改动，也是唯一需要你裁决的**。
- **已读口径要一并复核，且现状比"该不该同权"更糟**：站内取一次详情就写已读时间戳（没有"读完"这一档），而点开外链不产生任何信号——画像里站内浏览虚高、真实外链阅读全漏。足迹是个人版早报行为画像的输入源（口径见 `docs/features/my-reading.md`），这个偏差会直接喂进排序权重。**先定口径再动正文视图**，别做完才发现画像更不准。

**边界**：不改默认入口、不把阅读器做成无限流收件箱（这两件是 ADR-29 明禁的）；**本条不作"ADR-29 要求站内正文视图"的引申**——该件允许并要求的是"全部内容可检索回来"，站内正文属新增取舍，要做先在决策件立住。译文展示跟随现有降级语义，机翻必带来源标记（ADR-27）。

**什么算做完**：从"我的阅读"任一档进入能在站内读到正文（含已具备的分数／理由／译文）；要点与金句按你拍的口径落库或明确不落；已读判据有"读完"这一档并写回 my-reading 那份件；外链仍是可选项而非唯一出口。

### T6-6 深析打分偏低：先做截断对照，再决定改哪儿

与 T5-13 同一件事，这条补的是**T5-13 没记的一个变量**：深析调用喂给模型的正文只取前一段长度（另有摘要截断，具体取值读实现）。深度长文被截到那个长度后，"深度/实用/创新"这几维天然给不上去——**T5-13 那批读数里的低分分布，有多少是"写得差"、有多少是"模型没看全"，现在没有读数为据**（分布数值以 T5-13 那份为准，本条不复写一遍，免得两处各自过期）。

**第一步只做实验，不改分数口径**：同一批文章分别按"现有截断"与"全文（或提高上限）"各打一次，比分数与六维分布的偏移量。ADR-15 定的是六维口径固定不可增删，本条**不动六维、不动 ADR-37 的入报门槛**，只回答"截断是不是低分的一部分来源"。

**为什么这条要排在门槛裁决前面**：低分分布压进入报门槛就是早报空栏（T6-2 四条成因之一）。截断若是主因，收紧选题／换 prompt／调门槛都是在给一个测量假象做决策；坑 #34 那一族早就警告过"不能凭感觉拍高门槛，否则早报直接空掉"。

**什么算做完**：有一份带来源的对照读数（同批、两种喂法、分布偏移），据此给出 T5-13 那个待拍项的建议选项（截断上限／深析 prompt／初筛阈值三者中动哪个）。

### T6-7 国内可达：绑自有域名，与"国内能访问"不是一件事

**动机（用户 10-08）**：线上现在只有平台默认域名（值见 `docs/HANDOVER.md` 生产域名那行，本文件不复述），希望绑一个国内域名让国内能访问。

**先把两件事分开——选错支会把成本花在不起作用的那半**：

- **支一 · 自有域名直绑现有读层**：平台默认域是**整域**级别受干扰，换成自有域名确实绕开这一层，属低成本高确定性的第一步。但它不改"后端仍在境外边缘"这件事：延迟与抖动照旧，仍受平台 IP 段波动影响。**能把"完全打不开"改善，不保证"稳定打开"。**
- **支二 · 求境内稳定接入**：要上境内节点或 CDN 就必须 ICP 备案，备案要境内主体与接入商，并把站点变成"面向境内公开的备案网站"。**这与 ADR-01「不做自有服务器全量部署」相撞**——要么先改那条 ADR，要么给它加一个"境内只做反代与加速、数据仍只在 Turso 一个落点"的例外。别在实现里绕。

**内容面的知情代价（动手前必须有人拍过）**：本站聚合境外源（含境内不可达平台的 RSS 与 X/YouTube 内容）并叠加 AI 生成摘要。**"自己能在国内打开"与"做成境内备案的公开站点"是两个不同的得受面**——后者把内容展示责任接到备案主体身上。计划里不许把这两者写成同一个目标。

**改动面比"域名散落各处"小，但有一处前科**：

- 前端与读层**同域部署**，换域名不动前端代码；读层 CORS 现状不构成新域名的门槛（取值读 `vercel.json`）。
- 仓内"线上在哪"只有一处基址实现（`lib/cloud-site.js`，可被环境变量覆盖，共用方是巡检脚本与打线上的测试）。**为什么盯这一处**：同一个字面量曾散在四个工具里各写一遍，其中一份指着早已下架的旧域，结果是"云端巡检"连续 8 天全量 404 而无人察觉——而那支脚本存在的意义正是发现云端挂了（前科全貌见该文件头注与坑 #42）。
- 所以换域**必须同批**：改这一处基址 → 跑一次巡检证实真打通 → 改 `docs/HANDOVER.md` 生产域名行。只验"浏览器能打开"不算，那恰好是 8 天无人发现那一型。

**什么算做完**：先有一句人拍过的目标（自用可达 / 公开境内接入）。走支一：自有域名在**真实国内网络**下把前台与后台各打开一遍并留证，巡检脚本对新基址真回 200；走支二：先落 ADR-01 的改动件与备案主体事实，再谈实施。

## T7 10-13 登记（用户点单三件，排期未拍）

### T7-1 README 更新到现状

README 头注停在旧日期，核心功能清单、三端形状、生产地址口径与现行部署面已漂移（正文本该只写"此刻怎么跑"）。做法是按 `ARCHITECTURE.md` 与 `docs/FEATURE_MATRIX.md` 逆推重写功能与部署段，不是逐行补日期。**边界**：README 是门面不是事实源——易变数字（测试数、源数、阈值）一律写"见 XX"，不许抄死值进来再烂一次。

**什么算做完**：新读者按 README 能跑起本地端、看懂三端分工、找到生产地址；文中没有一个需要随迭代维护的死值。

### T7-2 AI 多账号池 + 英文文章翻译全覆盖（并入 T6-3 的验收）

与 T6-3 是同一件事的目标侧：多账号轮询是手段，**"窗口内英文文章翻译全覆盖"是它要交出的结果**（10-13 用户点单）。T6-3 列的前置（账号维度读数先长出来、凭据一处定义、覆盖哪几端先拍、先与"让路做全"比成本）原样适用，本条不重复。**新增的一条边界**：覆盖目标以"发布进入窗口的英文条目翻译完成率"为读数，不许用"翻译队列已清空"冒充——队列空可能只是没入队。

**什么算做完**：T6-3 那四条（每账号调用/失败/撞限额的现读、切换留痕、耗尽不静默减量）之外，连续数日窗口内英文条目的翻译覆盖率达全量（抽样现读），且无单日配额透支事故。

### T7-3 存量 bug 清扫轮（常设）

周期性把 `docs/ISSUES.md` 观察中表与"等你裁决"表过一遍：能复现的修、不能复现的降级或销号、证据链补齐。与正常迭代的关系：清扫轮**不动**正在开发中的功能，只收已稳定区域的存量。**边界**：修什么走 AGENTS 品味第 3 条（先复现再动手）；清扫轮的产出是 ISSUES 条目数净减少，不是又开新坑。

**什么算做完**：每轮结束后观察中表的条目要么有结论（销号/修复）、要么有新的现读证据；不许出现"看过一遍但没动任何一条"的空转轮。
