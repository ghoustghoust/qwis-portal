# ADR-35 · 云端写路径只"标记 + 交给批次"，不在一次请求里等结果

- Status: active
- 拍板：用户 09-12（手动翻译形态选型）与 09-30 从开发记录中确认为现行决策
- 依据：现读两个真写入口的形状（一个只把待办写进设置里的一份清单，一个只把源的下次抓取时间置空），以及真执行者都在批处理侧

【是什么】
在读层（云端函数）里，用户按下的"刷新这个源""重新生成""翻译这篇"这类动作，**语义都是登记一个待办**：改一个标记、往一份待处理清单里加一条，然后立刻返回"已受理"。
**真正干活的永远是批处理那一侧**（下一轮到点的采集批次、下一趟翻译批次）。读层不亲自跑完那件事再回复。

【为什么】
两条理由，缺一不可：

1. **函数有存活时长上限**，而采集要出网、翻译要串行限速、生成要跑完整条管线——这些都在分钟级。在请求里等它，结果是请求先被掐死，用户看到一个空白页，而活其实干了一半。**"点了没反应"比"稍后才出现"更难排查**。
2. **写入方只能有一个**。采集批次已经在跑同一批源、同一张表；如果点一下按钮又在函数里直接采一遍，就是两处并发写同一条语义——熔断计数、下次抓取时间、去重判断都会被对方踩坏。本项目最大的一次停摆正是凭据被多处写坏那一类问题。

这条也是"为什么手动触发之后要先看到'已受理'而不是结果"的产品解释：**它不是偷懒的文案，是这个系统的形状**。

【边界】
- **禁止**在读层的请求处理里做长耗时外网抓取、模型串行调用或整批生成再返回。要新增"用户主动触发"的能力，形状只有两种：登记待办，或改标记。
- **禁止**让读层直接写采集批次正在写的那些列（源的失败计数、下次抓取时间、批次状态）。需要立即生效的判据，走"标记 + 下一轮读它"。
- **受理之后必须有可见的回读路径**：用户能在下一轮看到这件事的结果或失败原因。**禁止**"入队即成功、之后无声消失"——那是把异步的形状变成丢任务。
- 待办清单的**去重与顺序**属实现（读实现，与链路指南 §2.A 第 21 条那条护栏一起读——"人工点过的最前"这条取舍的承载处与现读位置在那条护栏里，本件不复述）。
- 本件不管具体超时秒数、批间隔、清单键名——易变参数与现场读数，读实现。
- 与 ADR-13（采集触发双档）不冲突：那条讲"谁来叫醒批次"，本条讲"用户动作怎么进入这条链"。
