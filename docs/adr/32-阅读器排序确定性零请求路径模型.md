# ADR-32 · 阅读器排序是确定性可解释公式，请求路径上零模型调用

- Status: active
- 拍板：用户 09-13 在三个候选里选定"确定性公式、无 AI"，09-30 自开发记录中确认为现行决策
- 依据：现读阅读器列表的排序实现（一次查询内算完、可游标分页）；模型分数以已入库字段的形式参与，不在请求时现算

【是什么】
阅读器列表的排序是一个**确定性公式**：同样的输入永远给出同样的顺序，顺序能用人话说清（哪些因素、谁优先），并且能在一次数据查询里连同游标分页一起完成。
模型不进入这一层——**列表请求路径上不做任何 AI 调用**。模型产出的分数只作为**已经落在条目上的静态值**被这个公式取用。

【为什么】
这一层要解决的是"我打开时先看到什么"，用户要能验证：刷新两次顺序不该变、往下翻页不该重复或漏条、看到一条排前面时能问出"凭什么"并得到答案。
模型给不了这三件事：它有随机性与版本漂移、它在同一批输入上两次输出可能不同、它无法为一次列表请求实时打分（既慢又花钱，还会让翻页时前后两页由两次不同判断产生）。
**"一处评分、处处生效"是这套系统的前提**：评分发生在入库时，排序只是消费那个分数。让模型直接决定顺序，等于把策展口径从"入库那一次的判断"挪成"每次刷新的即时推荐"，那是另一个产品。

【边界】
- **禁止**在阅读器/检索列表的请求路径上调用模型、embedding 或任何远程打分服务（包括"只给前 N 条精排"）。
- **禁止**引入推荐/相似度/协同过滤形态的排序。这一层的输入只有：时间、源的状态轴、已入库的分数与用户显式设置的条件。
- **禁止**让顺序依赖会话状态、随机因子或未记录的隐式上下文——不可复现的排序不能进这条路径。
- 排序必须与分页游标兼容（同一顺序键），**禁止**为提升观感在结果取回后再做一次只影响当前页的重排。
- 公式里各项的权重、加成天数、门槛值属易变参数，不在本件写死；要改权重先回答"改完为什么这条排在前面"仍能一句话解释。
- 策展层的排序（早报栏目、探索位多样性）不受本件约束——那是 ADR-24 与 ADR-16 的范围，它们允许用相似度与分数做组合优化，因为那里产出的是**一份固定下来的清单**，不是每次刷新都重算的视图。
