# ADR-13 · 采集触发用双档，并用触发密度换可靠性

- Status: active
- 拍板：用户 09-26（本轮复核确认）
- 依据：作业文件实测（两档触发条件与作业内分支）+ 平台侧丢轮记录（问题台账）

【是什么】
叫醒采集这件事同时挂两档：平台自带的定时 schedule，加一档仓外的 HTTP 触发器。两档都只表示"现在跑一轮"，**不携带"要采哪些源"**——采谁由库里每个源的下次抓取时间决定。批次排得比任何单个源的真实间隔都密。

【为什么】
定时任务在平台高负载时会延迟甚至整轮丢弃（本项目实测过连丢五轮）。因为空轮的成本只有几秒（扫一遍到期表、没活就退出），所以宁可把轮次排密：丢掉一半，最坏延迟也只是翻倍，而不是等到下一天才发现数据停着。

【边界】
- **禁止**为"省空轮"把触发条件改成"有任务才跑"——那正是要防的失效模式：触发链一断，没人知道数据已经不更新了。
- **禁止**在触发里携带源清单或时间窗参数；一切到期判断只看库。
- cron 表达式、作业清单、各源间隔的取值**只允许存在作业文件一份**，文档其余处一律写「见作业文件 / 功能矩阵」。理由：这些数值改过好几轮，抄出去的第二份从来没跟上过。
- 判"这一轮到底有没有真跑过"要看心跳里的运行记录，不看"配置文件里有没有那条 cron"——有表达式不等于会执行。
