# ADR-12 · 凭据一套口径：口令换令牌，请求带 Bearer

- Status: active
- 拍板：用户 09-26（本轮实测后收口）
- 依据：本地与云端鉴权实现实测 + 线上无凭据探针（敏感读与未知写路径同为拒绝）

【是什么】
本地与云端是**同一套**做法：用环境里的管理账号口令换一个令牌，请求带 `Authorization: Bearer`。不存在"云端一套 Cookie、本地一套 JWT"的分叉。读者侧只读接口公开，写与敏感读要凭据。

【为什么】
两套机制会让同一个功能在两端表现不同，排障时要先问"你在哪一端"。既然只有一只账号（ADR-11），签名与校验路径也只需要一份。

【边界】
- **一个假入口**：设置项里那个管理口令哈希键只是"不回显"名单的成员，把它设上不会让任何接口放行——真凭据在环境变量那几处（三处同步的规矩见 `AGENTS.md` §2.6）。
- **禁止**新增第二种登录方式（扫码、magic link、设备码之类）——那是 ADR-11 的越界。
- **禁止**给云端另写一套 Cookie 会话：两端同一条换令牌路径。
- 令牌有效期与存储位置属实现细节，不在本件写死。鉴权门在请求路径上的位置是形状，见 `ARCHITECTURE.md` §3.2。
- **改值必须同批改齐所有持有方**：本地环境、云平台环境变量、仓库密文三处之外，还有**外置触发器里内嵌的那份凭据**。漏掉这一处的表现是触发器静默连跪而链路上没有任何报错——本项目曾因此整链 403 停摆。轮换清单里必须包含它，"三处同步"这句话不完整。
- 凭据的具体值、名字与存放格位不在本件写死，位置矩阵见 `ARCHITECTURE.md` §6 与 `docs/HANDOVER.md` §1.5（后者是本地件）。
- **凭据与鉴权那几位系统自持键，永不做成设置面上可写的键**：真凭据的生效位一旦变成"改一行配置"就能动的东西，任何一次误写、任何一段第三方脚本都能改走口令哈希、换掉备份指针或顶掉采集令牌——而它在库里看起来只是"用户改了个设置"。这类键只许由环境变量与仓库密文那几处持有（三处同步见 `AGENTS.md` §2.6）。
  - 现状：**云端设置写入口有一道保留键清单，命中即整次请求拒写**（顶层与嵌套都判）；名单的唯一住在实现里，本件不复制键名。**本地端没有这道挡**——它整段可写，这是两端的既有差异，不是待补的同步项（见 `docs/features/settings-plane.md`）。别把"云端拒写"读成"两端都拒写"，也别反过来把本地端的行为当基准。
  - **禁止**为了让某个运维项"能在界面改"而把它塞进可写名单。要开口子先推翻本件，并说清楚这个键改了之后谁能把它改回来。
