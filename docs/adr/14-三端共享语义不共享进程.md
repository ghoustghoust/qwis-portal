# ADR-14 · 三端共享语义，不共享进程

- Status: active
- 拍板：用户 09-26（本轮复核确认）
- 依据：三份采集实现与共用 `lib/` 的实际边界实测

【是什么】
本地、云端读层、runner 是三份独立实现，**共享的是语义不是代码**。真正需要一份的只有跨端都得同规则的那几件事，它们住在 `lib/` 里（熔断、保留、四轴、预配额〔本地灾备端有意不接这一层，分类理由见 ADR-09〕、噪声、密钥掩码、图片安全取回）。其余各端按自己的运行环境写自己的那份。

【为什么】
三端的运行约束根本不同：本地能跑无头浏览器和同步阻塞、runner 有长驻进程、读层有存活时长与函数配额。强行一份代码跑三端，等于把最弱那个环境的限制乘到全部三端上；而语义不分叉才是用户能感知的正确性（同一批源在**云端两侧**不该给出不同的入报结果；本地灾备端对预配额层的豁免是显式决策，见 ADR-09）。

【边界】
- **禁止**把"共享语义"实现成"同一份代码三端 require"——那会把不可移植的依赖带进 serverless。
- **禁止**在只改一端的实现里顺手改掉共同语义（过滤、清洗、去重、UA、间隔、熔断口径）；改这些必须对另外两份。
- **禁止**再用"两套部署同构同码"这类说法描述两端关系——语义一致、代码独立，是这个项目的既有形态。
- **不要求**"每个功能本地 + 云端各写一遍"：那是门户时代的旧默认，已废。顺序规则见 `AGENTS.md` §1。
- 哪些键真的被共用、哪些已经各自漂移，属现场读数，不写进本件。
- **"只许一份实现"是归属裁决，不是实现说明**。下面这批语义已经裁过"必须有且仅有一份出处"，新增同类时要先归进这个口径，别再长出副本：日报栏目表 · 标题类字段的 XML 实体解码 · 北京日界与日历日口径 · 早报候选层的每源配额 · 判"代码里真写了这句话"的词法扫描。本件**不写**它们各自在哪个文件、怎么实现——那些是现场读数，归 `docs/CLOUD_PIPELINE_GUIDE.md` 的护栏与 `docs/features/`。
- 一份实现收到一处之后，**对账方式必须同时存在**（能从事实反查、不靠人记清单）。"只许一份"没有对账，就等于没人知道它漂了。
- **同一裁决覆盖"一个数值被多处取用"**：一个跨端必须相同的常数（池子读多大、每源给几个坑这类）与"一份语义"同罪——只许一处定义、各处同取，并要有一把锁钉"不许分叉"。现例见 ADR-33；本件**不复制**它的取值，取值读实现。
