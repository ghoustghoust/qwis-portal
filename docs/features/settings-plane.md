# 设置面 · 用户改一项设置之后到底发生了什么

> 模块地图里「设置写入通道」这几行的承载文档。写的是**这条链现在怎么跑、哪里会骗人**，不是接口说明。
> 入口只有三处：本地端点、云端端点、生产链路里那份自写逻辑（路径见下文各节）。具体取值一律现读代码——**本文不复制易变数字**。

## 一、这条链的形状

```
用户在界面改一个值
   → PUT 到"他正在用的那一端"的设置端点
   → 写进那一端连着的那份库（本地库 / 云端库，两地互不同步，ADR-17）
   → 消费方在"它下一次读"的时候才看见
   → 页面或下一批产物变化
```

**第一问永远是"你改的是哪一端"**。同一个界面词在两份库里可以各有一份值，改了本地那份，生产链路看不见——这不是 bug，是 ADR-17 知情接受的代价。

## 二、三端写通道的规则**不一样**（这是"界面改了不生效"那一族的根源）

| 端 | 它怎么决定"这个键收不收" | 未知键的下场 |
|---|---|---|
| 本地 Express | 只按"认识的区"逐个分支处理，**没有白名单也没有保留键清单** | 没有任何分支接住 → **一个字都没写，照样回"成功"** → 前端提示已保存、回读显示默认值 |
| 云端读层 | 认识的区比本地多，另外带一张**系统保留键清单**（凭据与自写状态那一类），命中就整次拒绝 | 同样静默忽略并回成功，只是保留键那一挡是明确报错的 |
| 生产链路（采集/生成作业） | **没有面向人的写口**；它只写机器自写的状态键（心跳、事件缓存、归档、画像、待删读数、队列） | 不适用 |

两条必须记住的例外：

1. **云端"AI 配置不可写"这句话只在主设置端点成立**。另有一条专门管 AI 配置的端点，它真的会把模型、接口地址、密钥写进云库——而且**执行时以库里那份优先于环境变量**。现行口径是"保留可写 + 写审计 + 变更告警 + 写后探测失败即回滚"（四条各自落地到哪一步，见 `docs/CLOUD_PIPELINE_GUIDE.md` §6.1 与 `docs/ISSUES.md` 那条阻塞账）；主设置端点继续拒写这一段，**理由是"两个写入口只留一个真写入口，免得绕过审计"，不是"AI 配置只能来自环境变量"**——那句旧禁令与实际实现不一致过，纸面禁令挡不住真实通道。判"有没有写点"要按端点逐个看，不能按段猜。
2. **本地端 AI 段可写**（它没有那两道挡），本地库与云库又不同步，于是同一项"AI 设置"在两端是两份互不相干的值。

## 三、取值优先级：有一处**回显与执行顺序相反**

- 本地：环境变量与库里两份都在时，**环境变量赢**，且回显给界面时也按这个顺序——一致，界面说的就是真的。
- 云端 AI 段：**回显只看环境变量**（界面据此告诉你"现在用的是 env"），而**执行时先看库里那份**。于是出现最坏的一种失真——"存了、显示也对、运行时没变"，而且界面自己暴露不了这件事。代码里那句注释（"settings 覆盖优先级高于 env，改 key 永远修不好"）就是这次事故的墓志铭。
- 云端其余键：就是库里那份，没有双来源。

这条是缺陷不是设计，账在 `docs/ISSUES.md`（设置面那一族三型失真）；在它修好之前，**任何"改 AI 配置"的动作都要用一次真实调用去验，别看界面显示**。

## 四、从"按下保存"到"页面变了"之间隔着几层

1. **写进哪份库**（第二节）。
2. **读侧短缓存**：本地读层与云端读层各有一份进程内设置缓存，写入会刷新本实例那一份；Serverless 多实例、本地多进程之间，另一份最长在整个窗口里仍是旧值。人工连点时"没生效"经常只是撞上这个窗口——窗口取值现读那两份常数，本文不写。
3. **生效时机分两类**：绝大多数设置**只在下一个批次被读到**（采集、翻译、成报各按自己的批次）；只有读层的展示类设置是下一次请求就变。所以"改完看不到变化"要先分清它属于哪一类，再决定是不是问题。
4. **坏值的下场三端三套**（这是第三型失真）：
   - 有的**回落代码缺省并出声**（日志里有，界面上没有）；
   - 有的**静默回落**（连日志都不写）；
   - 有的**写侧抛错把整个端点带崩**，读侧回显时又把同一个非法值钳成默认——即"存进去的那份和显示的那份不是同一个东西"。
   
   共同点：**界面不会告诉你值被回退了**。要确认生效档位，只能现读库里的原始值 + 看一次真实批次的行为。

## 五、设置键分三类，混了就会长出没用的格子

| 类 | 判据 | 处置 |
|---|---|---|
| 人可配、有写口 | 有端点分支接住，且读侧真取它 | 正常路径 |
| **代码在读、没有任何写点** | 全仓搜不到对这个键的写入 | 它永远吃代码缺省。**这不是"忘了做一个输入框"**：真要调它得先决定开不开写口——AI 段那条真写入口只放行"模型 / 地址 / 密钥"三项，要不要把节流间隔与初筛门槛也放进去，是现行口径的续篇（账在 `docs/ISSUES.md`，含"运维键 vs 人可配键"要不要显式分类那一问） |
| **机器自写、人只读** | 只有生产链路写它 | **不该做格子**。兴趣画像是这一类的裁定样本（ADR-23）：每批整表重算，人工填了下一批就被算没 |

判"某个键该不该做成设置项"，先问它属于哪一类；问完再谈界面。

## 六、不能做什么（改这条链之前必读）

- **不许在某一端另起一套"什么算合法键"的判定**。三端各一份必然漂，现在已经漂成三种形态（本地连清单都没有、云端有保留键清单、生产链路根本不接受人写）。要收敛就收成一份共用判定，不要收成三份。
- **不许对未知键回"成功"**。静默假保存是唯一会主动骗人的形态；要么明确拒绝并说清哪个键不认，要么补齐分支让它真生效。
- **不许把"键存在于库里"读成"键可配"**，也不许反过来——把机器自写的状态键当成"用户没设置所以显示默认"。
- **不许为"界面统一"把机器自写的键暴露成可写**（第五节第二、三类）。
- **凭据类键不进设置面的写入通道**——保留键清单是这道防线，加新键时先问它算不算凭据/自写状态。
- **不许只看界面回显就宣布"改好了"**：在回显与执行同序的那些项上回显够用，在云端 AI 段上不够用（第三节）。

## 七、现在坏着的（不在本文复述，只指路）

| 事 | 账在哪 |
|---|---|
| 三型静默失真（未知键回成功 / 回显与执行反序 / 坏值三套下场） | `docs/ISSUES.md` 设置面那一族 |
| 决策路径上却无人能改的键，与"运维键 vs 人可配键"的分类义务 | 同上，另一条 |
| 生产配置表里躺着测试写入的残留脏键（清它属生产写，需授权） | 同上 |
| 周刊那个键在现役库里根本不存在，"可写但不生效"无从谈起 | 同上 |

## 八、怎么验（现读法）

- 看某一端到底认哪些键：读那两端的设置 PUT 分支，别读文档。
- 看某个键有没有写点：全仓枚举读取点与写入点对照（一条 grep 就够，方法写在 `docs/ISSUES.md` 那条的取证里）。
- 看一次改动真生效没：改值 → 等一个批次 → 现读库里原始值 + 产物行为，**不要以界面回显为准**。
