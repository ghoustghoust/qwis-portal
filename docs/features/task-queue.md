## 设计目标

- **不引入 Redis**：项目哲学自包含，PM2 单 fork，SQLite 足够（决策边界见 ADR-10：这套派发不引入外部队列中间件）
- **优先级排序**：带"特别关注"标记（27b 的聚光灯轴，旧称"重点/focus"已退役）的源排更前，其余普通档
- **同源去重**：同一 source_id 同时只允许 1 个 running
- **崩溃恢复**：进程重启后自动将 running 任务重置为 pending
- **可回退**：`QUEUE_ENABLED=false` 环境变量回退串行模式（不经过队列，走串行 await）

## 数据模型（语义，不是建表语句）

一张持久化任务表，每行装：任务类型（如抓某个源）+ JSON 负载 + **状态机**（`pending → running → completed | failed`，failed 重试耗尽后进 `dead`，dead 只能人工从队列面板重试）+ 优先级 + 重试计数 + **同源去重键** + 失败原因 + 三个时间戳。按"状态 + 优先级"和"源 + 状态"建索引。

## 怎么运转（只列步骤与产物）

1. 调度器扫到期源，逐个入队（带优先级与源 id）。
2. 持续消费：按优先级取 pending → 同源去重检查 → 标 running（尝试次数 +1）→ 交给该类型的处理器 → 成功标完成、失败标 failed 并记原因。
3. 启动时先做崩溃恢复（把遗留的 running 重置回 pending），再按配置启动持续消费与定期重试扫描。

## 重试策略

- 尝试次数未到上限 → 按**指数退避**延后重新入队（有封顶，上限值读实现）；
- 到上限 → 置 `dead`：不再自动重试，只能人工重试。

⚠️ 两个历史上真咬过人的坑（注释留在实现里）：
- 重试判定**不能**用 SQLite 的字符串列做数值比较（类型序 `INTEGER < TEXT` 恒假 ⇒ 重试永不发生）；
- dead 判定要放在循环内，**不能**在查询里预过滤（那样放不进去就永远不可达）。

## 注意事项

1. **SQLite WAL 模式**已启用，任务表与业务表共享无写锁竞争
2. **进程内内存锁 + SQLite 持久化**双重保障
3. **未知类型任务**标记 failed 而非崩溃（记日志）
4. **重试上限**：尝试次数到上限后不再被重试扫描重置
