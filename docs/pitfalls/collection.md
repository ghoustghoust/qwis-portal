# 坑 · 采集与信源（collection）

### #4 抓取必须限速超时（2026-08）
- 症状：抓取挂死、整轮采集超时。
- 根因：无头抓取/全文补抓无超时无间隔（微信 3s/篇）。
- 规则：所有外呼 fetch 必须带 `AbortSignal.timeout`；对同一站点串行+间隔。

### #6 调度器串行是有意的
- 症状：改并发后抖音/B站被秒封。
- 根因：平台风控按并发指纹封禁。
- 规则：抖音/B站保持平台级互斥串行；RSS 可并发但每源独立超时。

### #7 熔断机制
- 症状：源"消失"。
- 根因：连失 3 次（YouTube=10）自动 enabled=0，属设计行为非 bug。
- 规则：排障先查 sources.fail_count/enabled；修好后手动启用会清零；反爬类失败勿逐条报警（见 #29）。

### #9 采集语义三份实现漂移（最重量级）
- 症状：修了本地云端不生效，或反向。
- 根因：`server/services/collectors/*`（本地）、`api/collect.js`（Vercel 备份）、`tools/collect-turso.js`（云端主链路）三份独立实现。
- 规则：改过滤/清洗/熔断/去重/UA/钳制任何一处，**必须同步检查另两份**（2026-09-13 pubDate 钳制即三处同步修）。

### #19 newsnow 热榜 API 必须浏览器 UA（2026-09-11）
- 症状：29 个热榜源全 403、19 个被误熔断。
- 根因：自定义 UA（qwis-collector/1.0）被 newsnow 拒绝。
- 规则：UA 统一 Chrome，三处实现各有一份，改要同步。

### #28 大窗口读查询禁止携带 content_html（2026-09-13）
- 症状：weekly 模式启动即 `Fatal: terminated`。
- 根因：7 天窗口 × 2000 行全文一次拉取，libsql HTTP 链路被掐断。
- 规则：大窗口候选查询只取轻列，全文按 id 单取（两步走范式，参考 runTranslate）。

### #29 YouTube 反爬假 404 是常态（2026-09-11 起）
- 症状：YouTube 源每轮 20-80% 概率 404/500，92 源反复熔断。
- 根因：GH runner（GitHub 托管机房 IP）被 YouTube 识别为数据中心 IP 掷骰拒绝——**源是活的，IP 是死的**。与 Vercel 无关（采集不跑在 Vercel）。
- 规则：①熔断阈值按类型分档、**视频类必须保持放宽**（取值唯一承载处在 `lib/source-breaker.js`；曾因把视频类统一到小阈值而集体误杀活源，见 #7 与 #35），勿把视频类改回与图文类同档；②反爬类失败不逐条报警，熔断后走每日汇总；③根治靠换现成 RSS 源（决策见 ADR-25），不要自建爬虫。

### #30 源频率分层（2026-09-13 立项）
- 症状：更新刻度不统一（X 6h、公众号几天一次或一小时腹泻式多篇），源数破千后必然过载。
- 根因：全源共用默认间隔，无分层。
- 规则：新批量导入源按层级写 `extra.intervalMin`（runner 与本地 _shared.js 都认）：Top 级 60min、普通 180min、播客/周刊 360min+；后续演进为自动频率自适应（T4）。

### #35 熔断是"关进牢房"而不是"过一会再试"：三端自愈语义不一致（2026-09-18 实测）
- 症状：用户报「采集失败、自我熔断、YouTube 容易挂这些问题非得登录后台一个一个点重启，源又没坏」。
- 实测（只读评测，抽样 23 个熔断源真发重试）：**18 个（78%）当场成功**——6 个 YouTube 假 404、3 个 xgo 桥 `SERVER_ERROR 400`、2 个 403、1 个是我方解析器 bug（`value.toString is not a function`）。云端另有 195/210 熔断源 `lastErrorAt > frozenAt`，即"自动恢复后又坏"，间隔中位 **6.2 小时**。
- 根因（四条叠在一起，缺一不可看懂）：
  ① **熔断极易**：3 连跪（YouTube 10）就 `enabled=0`，而每轮节奏 15min → 一次 **45 分钟**的抖动就够锁源；
  ② **恢复极慢**：runner cleanup 的自动恢复门槛是冻结 **48h**（`resumeCount>=3` 后 **7 天**），而 cleanup 每天只跑一次 → 实际不可用 48~72h；
  ③ **错误性质不分**：反爬掷骰、我方解析 bug、真 410 死源走同一条 `fail_count` 判据（写在 `tools/collect-turso.js` 的失败登记那一段）；
  ④ **本地端零自动恢复**：`server/services/collectors/store.js` 的冻结那一步只置 `enabled=0`，恢复入口全是手动端点——实测本地 **584 个源锁死 5~7 天**，其中 **458 个 `lastErrorAt` 全落在 09-13T03 同一小时且错误一律 `fetch failed`**：一次代理故障把整库批量熔断，此后无人点击就永远不回来。
- 规则：
  ① **系统性故障不得折算成单源失败**——但判据**必须走三闸门**（量级 + 同源性 + 环境类，写成一处共享实现，见 #39 与 `lib/source-breaker.js` 的系统性故障判据）；只看"失败率高 / 错误长得像"一刀切的朴素修法会把真死源集体赦免（#39 论证过为什么错）。命中时本轮不 `fail_count++`、不熔断，只发一条出口报警；
  ② **冷却时长由错误类别决定**，不由连跪次数决定；`parser-defect` 一律**不熔断**（锁源＝把自己的 bug 藏起来），只有确认 `gone` 才进长冷却与人工队列；
  ③ **恢复前必须先探活**，探活失败就延长冷却，不许无条件放回（现 `restore-all` 是无差别解冻，且不清 `frozenAt/resumeCount`）；
  ④ **三端自愈必须同一份实现**（落 `lib/`，`server/`、`api/`、`tools/collect-turso.js` 三端引用）——本条正是"同一个源在本地永不恢复、在云端 48h 后恢复"的分叉代价；
  ⑤ 自愈必须留痕并在后台可见，否则用户看到的"源自己好了又自己坏了"比手动点更不可信。
- 案例：2026-09-18 熔断存量 云端 210（youtube 100/rss 67/x 39/hotlist 3/bili 1）+ 本地 584（**09-18 读数，未复测**；09-23 现役库熔断中 = 11 个源）；原方案 35 号 spec（35A 自愈引擎 / 35B 成功率数据地基）**已于 09-23 作废删除**，锚点见 `docs/ISSUES.md`「作废登记」一节；问题挂 `docs/ISSUES.md` H14/H15/H16 —— 其中 **H16 半边已交付**（`lib/source-breaker.js` 的系统性故障判据只在 `tools/collect-turso.js` 生效，另两端未接）。

### #39 大规模失败要先分清「我们出不去」还是「源真死了」，否则抑制器会变成永久免死金牌（2026-09-19）
- 症状：一次代理故障把 458 个本地源集体记为失败并逐个熔断，第二天后台一片红，用户只能一个个手动解冻（`docs/ISSUES.md` 坑 #35 的同一事故面）。
- 朴素修法为什么错：「一轮失败率高 + 错误长得一样」就整体不计数。这在代理故障上对，但**一批同源 404**（上游换域名、聚合器集体下架）也满足同样的形状——照这个判据，真正死掉的 30 个源会被集体赦免，永远不再熔断，坏源继续每轮浪费配额。
- 规则：三闸门缺一不可，且写成一处共享实现（`lib/source-breaker.js` 里的系统性故障判据）
  1. **量级**：一轮 ≥30% 到期源失败，或失败绝对数 ≥20；样本 <5 个直接不判（否则 1/1 = 100%）；
  2. **同源性**：失败里 ≥60% 是同一错误指纹。指纹要归一（URL/IP/端口/uuid/数字全打码），否则「换个端口就算两个错」；
  3. **环境类**： dominant 指纹必须命中网络/环境特征（ECONNREFUSED / ETIMEDOUT / EAI_AGAIN / TLS / 代理 / 429 / 503 …）。源侧 HTTP 4xx/5xx 一律照常计入各源。
- 抑制时做什么：仍写 `status='error'` 与 `extra.lastError`（保留排障线索），只**不累加 fail_count、不熔断**；日志与批次统计里标 `systemicSuppressed`，让人知道这一轮是被抑制的而不是"真的没事"。
- 分母陷阱：判系统性时 outcomes 必须**同时记录成功与失败**。只 push 失败会让失败率恒为 100%，任何一次小批量都"系统性"（回归锁 F6-3 专门钉这一条）。

### #73 改了抓取间隔却不重算"下次抓取时间" → 新配置要等老 deadline 到期才生效，看起来像"改了没生效"（2026-09-08 立项，2026-10-01 从归档件里核实现状）
- 症状：把某个源从 60min 调成 15min，界面上回显变了，但它在接下来将近一小时里一次都没被采。
- 根因：调度判的是"下次抓取时间到没到"，不是"这一轮的间隔配置"。只写频率值、不把到期时间往前顶（或置空让它立刻到期），改动就得**等上一轮的 deadline 走完**才起作用——最坏情况比新配置本身还慢几倍。
- 规则：**任何写频率的路径，必须在同一次写入里一起处理到期时间**（顶到新的更早点位，或直接置空让下一轮立刻采）。这条与 ADR-14"共同语义只许一份实现"同族：
  - 现状是**只有一端做对了**：本地端改单源频率时会立刻顶到期时间；**云端批接口和"整组调频"那条单条 SQL 都只写频率、不动到期时间**（已登记为缺陷，账在 `docs/ISSUES.md`）。
  - 新增任何"批量改频率"的入口时，别只写那个值：把到期时间一起算进去，或者显式说明为什么这次不需要。
- 现读法：改一个源的频率，立刻读它的下次抓取时间与最近抓取时间；再等一轮批次，看它是否按新频率回来。间隔取值口径见 `docs/features/collectors.md`。

### #74 托管 feed 的"最后更新时间"常常就是你发起请求的那一刻 → 拿它判"内容新鲜度"永远得到"很新鲜"
- 症状：为了证明某个源停更，读它 feed 根节点那个更新时间戳，结果是"刚刚"，于是判"源活着"。而条目本身已经几周没动了。
- 根因：不少 feed 生成器把**通道级时间戳写成渲染时刻**（Atom 的 `updated`、RSS 的 `lastBuildDate` 这类），它是"这份 XML 是几点生成的"，不是"最新一条内容是几点发布的"。归档那批审计报告里曾有 4 份互斥结论，其中一条就是这么错来的（该报告已作废，反查走 git）。
- 规则：**判新鲜度只看条目自身的时间字段，且要和库内落地时间对账**。
  - 逐条时间字段缺失或全等于请求时刻 → 判"这个源没有时间口径"，这是结构性缺陷（它在任何时间窗查询里都永久出局），不是"停更"也不是"正常"。
  - 不许用"抓取成功 / HTTP 200 / feed 能解析"当新鲜度证据——那三件事只证明通路通。
  - 要证"停更"，读库里该源最后一条内容的发布时间与它距今的天数（现读法：`docs/RUNBOOK.md` §6 健康自检与报警 + 后台问题源视图）。

### #76 熔断里混着大量"能好但没人工恢复"的活源：试探恢复要分批、可回滚（2026-10-02 实测）
- 症状：源列表一整片红，看上去"全熔断了"。但实测 YouTube 熔断源里 125 个中选 15 个分批试探恢复，第一轮采集即 **15 活 / 0 再熔**，两三轮后仍 15/15 启用、累计失败计数为 0——这批当时根本不是真死，只是云端没有自动恢复线（H14），失败计数攒到阈值后没人把它们放回来。
- 根因：熔断的设计是"关进牢房等人工"（坑 #35），而反爬掷骰类失败（YouTube 对机房 IP 的假 404/500）会持续触发计数，真死源与"临时被误伤"的活源混在同一个熔断池里分不开。
- 规则：**恢复必须分批、带备份、可回滚，且效果用探针读数判，不靠"点了恢复就完事"**：
  - 分批 = 防二次熔断（大批同时抓取集体失败再被熔断，见 RUNBOOK §5）；一批的量级十几二十个，不是全量。
  - 解冻动作 = 置启用 + 清 fail_count + 清 extra.last_error + 把 next_fetch_at 顶到立即到期；保留间隔与校验标记，不整列清空。
  - 写前整批备份，工具带 --undo；extra 里落 restore_probe 审计标记。
  - 判"活没活"读采集后每源的 fail_count 与 last_fetched_at，活/再熔分桶；一轮全活不等于稳，反爬掷骰要连看几轮。
  - 现成工具：`tools/probe-restore-frozen.js`（dry-run 默认，--apply 需显式带刚写的备份路径防误触）。
- 案例：2026-10-02 YouTube 117 熔断源中的首批 15 个，首轮 15/15 活、连续多轮零再熔；备份 `docs/eval/restore-youtube-2026-10-02T1241.json`，账在 `docs/ISSUES.md` H14/H15。
