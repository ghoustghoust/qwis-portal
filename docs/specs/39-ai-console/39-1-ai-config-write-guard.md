# 39-1 · AI 配置写回面：可写 + 审计 + 变更告警 + 探测失败回滚 —— 小 Spec

> 总框架：`spec.md`（39）。状态：**待批准**（涉及云端写路径行为变更；UI 呈现归 `docs/specs/38-admin-ia-refactor/38-e-ai-console.md` 的 E1~E3）。
> 决策依据：用户 2026-09-19 裁决——**保留可写 + 强制审计 + 变更告警 + 写后连通探测失败即回滚**；
> 旧的"env-only"表述已在 `docs/CLOUD_PIPELINE_GUIDE.md` §6.1 标「已作废」并留链接（不许静默删除）。
> 最后更新：2026-09-19

## 背景：专用口写、通用口拒——**入口收敛本身是对的**，但通用口的文案还在执行一条已作废的决策

实测两条写路径（都在 `api/[...slug].js`）：

| 入口 | 行为 | 判读 |
|---|---|---|
| `PUT /api/settings` | `body.ai` → `400 云端 AI 配置锁定为环境变量（AGNES_*），请在 Vercel 环境变量中修改` | 拦截本身符合裁决（AI 只有一个写入口）；**但理由与文案是 09-11 的 env-only 旧决策**，注释还写着「F4：AI 区云端锁定 env-only（2026-09-11 settings.ai 污染事故决策）」 |
| `PUT /api/ai/config`（`handleAiConfig`，行 1426-1448） | 直接写 `settings.ai.{model,apiBase,apiKey}`，**无审计、无探测、无回滚、无告警** | 这才是"保留可写 + 四件套"该落的地方，目前四件套一件都没有 |

所以真问题不是"两个入口互相矛盾"，而是：**裁决改了，实现只改了一半**——
①通用口把用户往"去改 Vercel 环境变量"指（与 2026-09-19「保留可写」的裁决相反，且后台界面就摆着保存按钮）；
②专用口该加的审计/告警/探测/回滚全缺（`npm run eval:preflight` 已如实报：`可写通道开着，审计未落地=BL9`）。

风险量级：09-11 那次全链路 401 停摆 2 天，根因就是 `settings.ai` 被写坏（`apiKey` 被覆盖成占位值），
而这条通道今天仍然开着、且**无人知情**（无审计、无告警）。

（订正说明：本文件第一版把上面两行读成"同一个决策两份实现给出相反答案"，那是我把"入口收敛"误读成"策略冲突"。
写进文档是为了让下一次不要重犯：**先确认设计意图，再定性缺陷**。）

## 目标

把"可写"变成**有回执的可写**：一次改动留下 who/when/before/after/探测结果，探测失败自动回到改前值。

## 功能点

| # | 内容 | 判据（可测） |
|---|---|---|
| P1 | 唯一写入口收敛 | `PUT /api/settings` 对 `body.ai` 从"拒绝"改为"引导到专用口"（400 + 指明 `/api/ai/config`）；除 `/api/ai/config` 外全库不得有第二条写 `settings.ai` 的路径（白盒新增检查项，与 W3b 同一实现风格） |
| P2 | 写前探测（可选但默认开） | 保存前用新参数打一次 `ping`；不通则**不写**并返回失败原因（避免把 key 写错后全链路 401） |
| P3 | 写后探测 + 自动回滚 | 写成功后再打一次；失败即把 `settings.ai` 还原成写前快照，并返回 `rolledBack:true` + 原因。**不许"写坏了等用户发现"** |
| P4 | 审计落库 | 每次写调 `auditRecord('ai.config.write', {before, after, probe, actor})`；`before/after` 里的 `apiKey` **只存指纹（前 4 后 4）**，永不存明文 |
| P5 | 变更告警 | 审计成功后推一条 `ai_config_changed` 事件；**送达判据复用 `lib/alert-channels.js`**（当前 BL7 未恢复，这条必须是红的，不许显示"已通知"） |
| P6 | 读侧维持现状并加锁 | `GET /api/ai/config` 只回 `apiKeyConfigured` 布尔（实测已是如此）——加回归锁防"以后有人顺手回显明文" |
| P7 | 频控 | 同一进程 60s 内连续改 `settings.ai` ≥3 次 → 拒绝并告警（防止被脚本/测试打穿） |

## 边界

- **不改** env → settings 的优先级语义：仍是 `settings.ai` 覆盖 `AGNES_*`（档位优先读不变量），本 spec 只管"写进来这条路"。
- 不在本 spec 里做提供商列表代理（39-3）、运行台统计（39-4）、prompt 编辑（39-5）。
- 明文密钥不进代码、日志、审计、报告（`util/log.js` 已有脱敏，本路径必须走它）。
- 不动 `settings.alerts.channels`（那是 37-1 的写回守卫，同一套思路但不同键）。

## 验收标准

- AC1：端到端——在隔离环境把 `apiKey` 改成一个必然失败的值，界面必须看到"未写入/已回滚"+原因；`settings.ai` 回到改前值。
- AC2：审计与告警各一条锁：写一次 → `audit_log` 新增一条 `ai.config.write` 且**不含明文 key**（正则判据）；告警在 BL7 未恢复时必须是 `delivered:false` 可见。
- AC3：白盒新增项（P1 的唯一写入口）在全库跑通，且做过负向验证（塞一个假的第二条写路径必须红，删掉必须绿——EVAL_GUIDE §4.1）。
- AC4：F2P——每条新功能对应一条锁，`npm run eval:f2p -- --auto-base --tests tests/regression-2026xxxx.test.js` 出双证据。
- AC5：`npm run eval:preflight` 里 "settings.ai 未偏离 env / 审计是否落地" 这条判据要从"提示"升级为"审计缺失即红"（当前是提示，因为裁决刚定、实施未做）。

## 需要用户确认

1. P3 的自动回滚是否无条件开启（我倾向：是；代价是"故意写一个不通的 key 做实验"会被回滚，需要显式 `--allow-unverified` 才能留）。
2. P1 对 `PUT /api/settings` 的 `ai` 键：改成"引导"还是继续"硬拒"？两者都自洽，但必须只有一种答案。
3. P7 的阈值（60s/3 次）是否合适。
