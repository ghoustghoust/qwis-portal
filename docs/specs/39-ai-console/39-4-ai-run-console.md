## 目标

G-A 任何一个 AI 失败模式，**在后台一屏能看到：次数、占比、耗时分布、是哪一类**；
G-B 让"推理模型不吐正文"这类结构性失败**不再靠用户发现页面空白**（与 37-4 的 `ai_failed`/`summary_missing` 打通）。

## 改动点（批准后才写）

| # | 内容 |
|---|---|
| T1 | `GET /api/ai/stats?window=24h\|7d` → 按 `kind` 聚合 `{calls, fails, failRate, p50Ms/p95Ms, topErrors:[{sig,count}]}`；`sig` 用**错误归类**而不是整串原文（避免噪声与潜在敏感内容外显） |
| T2 | `ai.stats` 的写入要**带上 `mode`（哪条链路：translate/daily/weekly/mybrief/quickscore）**，否则聚合出来的"失败"无法归责——现在只有 `kind`+`provider` |
| T3 | 前端运行台面板（归 39 域 UI 或 38-G，**不重复立界面 spec**）：配额/限速视图要显示 `ai.minIntervalMs` 的**真实生效值**（见 BL8：线上该键存的是 `0`，而代码默认 4000） |
| T4 | 阈值事件化：`failRate > 阈值` 或单一错误签名占比 > 阈值 → 发 `ai_quota`/`ai_degraded` 事件（37-4 定义，本包只提供数据源） |

## 判据与验收

- AC1 `GET /api/ai/stats` 返回的 `fails` 必须与"逐条 `calls[]` 里 `ok===false` 的计数"**完全相等**（回归锁：同一份 fixture 两个算法对账，防"面板自算一套"）。
- AC2 滚动上限要说清：500 条 ≈ 不到 7 天就滚完（本轮实测 500 条恰好全部落在 7 天内），因此 **7 天窗口的真实总数不可知** → 面板必须显示"样本窗口=最近 500 次调用"，不许把它当"7 天全量"汇报（这一条本身就是对本文件上方数字的诚实约束）。
- AC3 T2 落地后，新写入的每条 call 必带 `mode`；老数据无 `mode` 要显式归入 `unknown` 而不是被过滤掉。
- AC4 与 37 域打通：`ai_quota` 事件的判据必须读这个端点/同一份聚合函数，**不许在报警侧再手写一份统计**（同 B107/B109 的病根）。
- AC5 F2P 按 **B106** 构造规则出证（新建实现文件在基线缺失 ⇒ `env`，不是"锁假了"）。
