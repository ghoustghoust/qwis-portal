## 一、从论文借什么（已核对原文）

| 论文机制 | 出处 | 我们的对应做法 |
|---|---|---|
| 任务有效性三条件：改前 ≥1 测试失败、失败者改后全通过、改前通过者改后仍通过（F2P/P2P） | §2.3 | 端到端断言分两集合：**F2P**=本轮改动对应场景，**必须先在"未含该改动"的分支上红过**；**P2P**=阅读器/早报/周刊/我的阅读/后台 5 Tab + 关键 API，每轮全绿 |
| 失败原因结构化（`failed_lite_validators`） | §2.3 | 每个 case 输出 `pass / fail_product / fail_env / fail_flaky`：代理 `127.0.0.1:12000` 不通、Vercel 边缘缓存 20s 残留（`DELIVERY_VERIFICATION.md` §3.1/§3.4）归 `fail_env`，**不算交付失败** |
| 依赖冻结（pip freeze） | §2.3 | 每次评测固化 `env_lock`：Turso 快照标识 + `APP_DATA_DIR` 副本（坑 #13 已有）+ `settings` 快照；报告带快照号才可复盘 |
| 题源绑定真实变更 + 质量只作元数据不静默丢弃 | §2.1/§2.4 | 每条 `docs/pitfalls/*` 必须对应一个 `tests/regression-*` 用例；`doc-lint` 加门禁「新增坑无同名测试 → 报错」 |
| 统一 scaffold 消除不可比 | §3.2 | **白盒一致性检查**：把三端采集实现（`server/services/collectors/`、`api/collect.js`、`tools/collect-turso.js`）的过滤/清洗/熔断阈值/冷却/UA/间隔字面量抽出来逐项 diff；`lib/brief-guards.js` 阈值、"多写者产物表按档位读"、"settings 覆盖 env" 同做常量断言 |
| 每题跑 5 次并报 SEM | §3.2/App. J | 端到端同剧本跑 3~5 次；`--test-concurrency=1` 后仍偶发者标 `flaky` 隔离，**不作通过依据** |
| 去污染＝时间切割 + 显式标记（不是文本查重） | §3.2/§3.3 | 见下节 |
| 安装验证仅 14% 通过是全链瓶颈 | App. L Table 6 | 我们最脆的是"三端凭据同步 + 代理" → 评测前必须有**环境健康前置检查**，不通过就中止而非误报缺陷 |

**明确不照搬**：21K 规模、爬 GitHub Archive、分布式容器、微调模型打质量标签（其测试补丁正确性仅 67%）、公开 leaderboard、**用 pass@k 当门禁**（论文 pass@5 是"5 次里中 1 次"，对交付太松；我们只把 pass@k 用于 flaky 定性，门禁必须"每次都过"）。

## 二、去污染：防"自己给自己出题、只测顺手写对的路径"

我们的等价污染不是训练数据重叠，而是**实现者同时是出题人**。四条可操作：

- (a) **自证标记**：case 记录 `scenario_added_at` 与 commit；与所验实现同提交同出处 → 报告标 `self_authored=true`，**不得单独作为验收依据**。
- (b) **强制改前失败**（最有效）：新 case 必须先在未含该改动的分支跑出红，抓不到 bug 就删掉这条 case。
- (c) **以矩阵为分母算覆盖**：拿 `docs/FEATURE_MATRIX.md` 的「页面 × 功能」格子当分母，脚本未覆盖的格子自动生成「已知空洞」清单进 ISSUES——把覆盖率从主观变机械。
- (d) **题源限定 + 对抗补测**：只从 ISSUES/批注、`/api/health/status` 与 `audit_log` 实发故障、pitfalls 事故里出题；每轮从未覆盖格子随机抽 1 个做异常组合测（空数据、档位切换、settings 覆盖 env、熔断中恢复）。长期全绿的饱和 case 归档换题。

## 四、边界

**不做**：不搭 CI 云端评测集群（本机 + runner 足够）；不做多模型对比榜；不把端到端跑进生产写路径（评测一律走只读端点或隔离库；需要写操作的场景在 `APP_DATA_DIR` 副本上跑）；不追求覆盖率百分比好看——矩阵空洞清单是给人看的，不是 KPI。

## 五、验收标准

- AC1（41-1）：人为关掉代理后跑评测，输出 `fail_env` 且**不**产生"产品缺陷"结论。
- AC2（41-2）：一次命令跑完 5 页 + 后台 5 Tab，产出结构化报告（pass/fail 分类、耗时、截图路径）；同一剧本连跑 3 次结果稳定，偶发者被标 flaky 而非算通过。
- AC3（41-3）：本轮任选一个已修缺陷（如 B28 类型筛选），能出示"改前红、改后绿"两份证据；F2P 集合里没有"改前也通过"的用例。
- AC4（41-4）：白盒检查能在人为制造"只改一份实现"时报警（例如把 runner 熔断阈值从 3 改成 5 而不同步另两端）。
- AC5（41-5）：生成当前覆盖空洞清单（预期会暴露大量空白，这是目的不是失败）。
- AC6（41-6）：AGENTS §3 与 `DELIVERY_VERIFICATION.md` 一致，且 `npm run lint:docs` 能挡住"新增坑无测试"。
