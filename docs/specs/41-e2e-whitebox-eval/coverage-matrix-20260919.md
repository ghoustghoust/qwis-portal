## 3. 汇总与结论

- **39 格里：✅ 3、◐ 8、⛔ 28**（≈ 72% 功能格没有端到端断言）。
- 缺口不是均匀分布，而是集中在两类：① **后台写回闭环**（需登录态，我不代你登录）；② **数据/采集面**（端到端结构上看不见）。
- 所以此前我说过的那句话要写死在案：`npm run eval:e2e` 的 10/10 ×3 **不等于**"交付面全绿"，
  它只覆盖前台渲染与响应自洽；B101（清理从未触发）这类故障**只有** preflight/心跳判据/白盒能抓，
  而"保留语义"目前**三层都没有**（这就是 43 号 spec 的 W17 与 37-5 的 `scheduler_gap` 要补的位置）。
- 另有一处**结构性反例**要记：`docs/ISSUES.md` 的 B26/B73 说明"同一端点冷启动 30.7s、热态 0.66s"，
  而 §3.5 的性能预算依赖端到端顺带测量 —— 冷路径没被触发时，剧本会**系统性地把慢端点测成快**（本轮 3 轮全绿即为此）。
  41-5 实现时应把"冷/热双峰"当一列显式记录，而不是只取 P95。

## 4. 交给 41-5 的验收要求（不在这页实现）

1. 生成器输出的分母必须 == 本页 §2 的 39 行（多算/漏算都算工具红）；新增功能格时**先**加矩阵行，再谈剧本。
2. 每格必须落到"哪个剧本覆盖 / 该由哪层覆盖（端到端 · 白盒 · preflight · 人工）"，**不接受"待补"这种空值**。
3. ⛔ 计数要进 `npm run lint:docs` 同级门禁（只许降不许升；要升必须在 ISSUES 登记为什么这次又多一格）。
4. **与工具的两个空值对账（这条是本轮自查出来的关键点）**：`tools/eval-e2e.cjs:1023` 的 `KNOWN_GAPS` 实测是**空对象**，
   `summary.uncoveredKinds` 也常为空 —— 但这两个空值**都不表示"功能覆盖完全"**：
   - `KNOWN_GAPS` 只登记"**剧本级**已知缺口（带 ISSUES 编号、从门禁摘出，防止用删剧本逃门禁）"；
   - `uncoveredKinds` 是**单条剧本内的三类断言（渲染/接口/数据）齐不齐**，与"39 个功能格有几格没人管"无关。
   也就是说：现有工具**没有功能格分母这个概念**，所以矩阵里 28 个 ⛔ 在它眼里根本不存在。
   41-5 的职责就是把分母引进来；引进后若与本页 §2 不一致，**以逐格可核对的实测为准**，差异本身要能解释。
5. 在 41-5 落地前，任何写进文档的 `knownGaps=[]` / `uncoveredKinds=[]` 都**不得**被叙述成"无缺口"（本轮已在
   `FEATURE_MATRIX.md` §1.5 的 e2e 行加了限定语）。
