## 背景与实测结论

| 现象（用户所见） | 实测根因 | 定性 |
|---|---|---|
| 「未知日期 30 条」置顶 | 云端 `/api/reading` 快路径 `api/[...slug].js:1134-1141` 漏 `AS date`（慢路径 `:1168` 与本地 `server/routes/reading.js:136` 都有）；前端 `MyReadingPage.jsx:128-130` 用 `dateKey(it.date)` 分组，`'unknown'` 按字符串降序排最前。**库里 80022 行中 published/created 双缺 = 0 行 → 不是数据缺日期** | 接口字段回归（09-13 T3-3 优化引入）+ 前端无兜底 |
| 文章/播客/视频筛选无效 | `:1173` `WHERE ${tabCond}${aExtra}` 未给 `tabCond`（`:1031` = `read_at IS NOT NULL OR later=1`）加括号，AND 优先级吞掉类型条件；实测 `type=podcast` 与 `type=all` 返回**同一批 id**，而同一响应的 counts 走另一条正确 SQL（`:1060-1063`）→ 数字与列表互相打脸。本地实现正确＝**三端漂移** | 接口 SQL 缺陷 |
| 类型口径本身错 | `播客 = s.type='douyin'`（云端 douyin 源 1 个、文章 **0 篇**），真播客口径应是 397 条音频 enclosure 文章；`文章` 类型表含死值 `'wechat'`，真实类型是 `wemp` → **881 篇永不出现在「文章」tab**；`视频` 只认 `favorite=1`（线上 0）且 tab=read 强制空 → 恒空 | 口径设计缺陷 |
| **口径收敛后的遗留语义问题（2026-09-19 B60/B61 之后）** | 四处副本已收敛为 `lib/reading-filters.js` 一份，但**收敛只保证"四处一致"，不保证"口径对"**。实测仍有两个待决策：①`视频` tab 只认 `v.favorite=1`，线上 `favorite=1` 为 **0 条 / 视频总 2813 条** → 该 tab 结构性恒空，需决定"阅读页视频"到底指收藏还是看过（看过要 B30 的云端 `watched_at` 回写）；②`type=all` 的 25142 条里 **17860 条（71%）来自 hotlist 聚合源** → 「我的阅读」被热搜足迹淹没，是否沿用列表页 `NOISE` 排除口径（`UI-D4/D5`）需拍板 | 语义设计缺陷（本 spec 36-1/36-2 处理） |
| 「各报放大读过的完整文章这里没有」 | 文章类**其实有**回写（`GET /api/articles/:id` 顺手置 `read_at`，真实已读 287 条：hotlist 105 / rss 149 / wemp 31 / x 2）；**视频/播客没有**——云端全文无 `UPDATE videos SET watched_at`（只有本地 `server/routes/videos.js:81`）→ 云端视频观看足迹永久丢失。用户的观感被上面两个 bug 掩盖 | 部分存在：云端写回链路缺失 |
| 阅读器卡顿 + 「像按源块排序」 | 排序**确实是时间**（`:152-154` smart = 时间戳 + spotlight×3d，`:175` `ORDER BY … DESC, a.id DESC`，无 source 分组）。相邻同源的真正来源：①同源成批发文；②时间戳并列后按 id 倒序 → 同一次抓取天然连号（单刻最多 132 条同 `04:00:00.000Z`，跨 12 源）；③今日 3234 条里只有 468 条来自 31 个 spotlight 源，+3d 加权把它们整体置顶；④云端 `/api/articles` **无 dedup=1 分支**（H7），重复事件不折叠。卡顿：smart 表达式无索引（实测 11.4/13.6/15.3s）+ 列表无虚拟化、`web/src` 零 `memo()` + 每点开一篇文章重拉 545KB sources 重渲侧栏（`ArticleView.jsx:56 → ReaderPage.jsx:95 → Sidebar.jsx:24`） | 排序＝观感问题（非缺陷）；卡顿＝真实性能缺陷 |

## 目标

- G1 「我的阅读」三个 tab × 三种内容类型的筛选与计数**自洽**（列表与角标同源同 SQL）。
- G2 日期分组永不再出现"未知日期"置顶（前端兜底 + 接口字段对齐）。
- G3 阅读足迹口径可信：视频/播客在云端也有写回；"点开即读"与"读完"区分开。
- G4 阅读器首屏与点击链路进入可用区间（P95 < 2s），不再"点一篇卡一次"。
- G5 三端（本地/云端/runner）阅读相关 SQL 收敛为同一构造函数，配回归锁。

## 板块拆分（每块各出 mew-spec 小 spec，批准后再写）

| 小 spec | 内容 | 类型 | 规模 |
|---|---|---|---|
| **36-1** | `/api/reading` 快路径补 `AS date` + 前端 `it.date \|\| published_at \|\| created_at` 兜底 + `'unknown'` 排最后 | 一行级修复 | XS |
| **36-2** | `tabCond` 加括号；快/慢路径共用同一 SQL 构造器；counts 与列表同源 | 一行级修复 + 防漂移锁 | S |
| **36-3** | 类型口径重定义：文章=`articles`（含 wemp）、播客=音频 enclosure、视频=`videos`；tab 与类型两个维度正交 | 口径变更 | M |
| **36-4** | 云端 `videos.watched_at` 写回链路（三端一致）+ 与 B18（videos 表无 score/translated_title）一并决策 | 能力补齐 | M |
| **36-5** | 阅读语义定稿：`GET 详情即已读` 是否保留；若区分"浏览/读完"需前端停留与滚动信号 | 产品语义 | M，需拍板 |
| **36-6** | 阅读器性能：smart 排序索引或强制 `since` 窗口、列表虚拟化 + 行 memo、点开与侧栏重拉解耦、`api.js` 5s TTL 策略 | 性能重构 | L |
| **36-7** | 同源打散与云端 dedup（H7）：smart 结果加"同源最小间隔"或事件折叠上云 | 排序体验 | M |

## 边界

**不做**：不改采集链路；不动 `articles` 表结构（除 36-4 与 B18 合并决策时的建列）；不做阅读进度条/收藏体系新功能；不在本轮解决"今日 3234 条"的信息过载（那是 spec 23 的七层防御）。
**注意**：`spec27` 的「今日视图几十条量级」前提已被实测打破（近 24h 可读 3234 条），36-6/36-7 必须显式回应，否则排序与性能结论都建立在失效假设上。

## 验收标准

- AC1（36-1）：线上 `GET /api/reading?tab=read&type=all` 首屏 30 条每条含非空 `date`；页面首个分组标题是日期而非"未知日期"。
- AC2（36-2）：`type=podcast` 与 `type=all` 返回集合不同且 counts 数字与列表条数一致（同一 SQL 推导）；新增回归锁断言"快慢路径字段集相等"。
- AC3（36-3）：文章 tab 能看到 wemp 条目（线上 881 篇中至少 1 条）、播客 tab 出现音频条目、视频 tab 出现视频；本地与云端同参数响应集合一致。
- AC4（36-4）：云端打开一个视频后，`videos.watched_at` 非空且出现在「我的阅读·视频」。
- AC5（36-6）：`/api/articles?sort=smart` P95 < 2s（当前 11~15s）；点击一篇文章后 Network 不再出现 545KB 的 sources 重拉。
- AC6（G5）：三端阅读相关 SQL 构造函数唯一实现，`npm test` 有跨端一致性用例；端到端评测（spec 41）覆盖上述 AC1~AC5 场景。
