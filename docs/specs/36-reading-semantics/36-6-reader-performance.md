# 36-6 · 阅读器性能：首屏与"点一篇卡一次" —— 小 Spec

> 总框架：`spec.md`（36，G4）。状态：**待批准，未动工**。预算口径：`docs/EVAL_GUIDE.md` §3.5（交互路径 P95 < 2s）。
> 最后更新：2026-09-19

## 现状（2026-09-19T22:45~22:46Z 线上直测，代理链路，三次连跑）

| 端点 | 实测 | 判读 |
|---|---|---|
| `GET /api/articles?sort=smart&limit=30` | **17.6s / 5.9s / 9.1s**（均 200，25.6KB） | 远超 2s 预算，且**双峰**（与 B26 `/api/status` 同形：冷路径跑全量重排序，热态回落） |
| `GET /api/sources` | **2.49s / 626,847B（612KB）** | 上一轮记的是 545KB，已随源数增长（`sources` 全量 1437 / 启用 1169）——**"点一篇文章就重拉整张源表"这件事的成本还在往上走** |
| `GET /api/reading?tab=read&type=all&limit=30` | 1.06s | 阅读页本身已可用（快路径 + `AS date` 落地后），不是本包瓶颈 |

前端侧（上一轮实测仍成立，本包动手前须复测）：列表**无虚拟化**、`web/src` 零 `React.memo`；`ArticleView.jsx` 打开文章 → `ReaderPage.jsx` → `Sidebar.jsx` 触发 612KB 源表重拉与整侧栏重渲。

## 目标

- G4a 交互路径 P95 < 2s：`sort=smart` 首屏、点开文章两条。
- G4b 点开一篇文章**不再**引起源表全量重拉（Network 里不该再出现 612KB 的 `/api/sources`）。
- G4c 冷/热双峰要么消除，要么显式降级为"先出轻投影、后补重字段"（与 B26 同一套路子，不许用"多等一会"糊过去）。

## 改动点（批准后才写）

1. **排序侧**：`smart` 表达式（时间戳 + `spotlight×3d`）目前无索引 → 二选一并测：(a) 建表达式/生成列 + 索引；(b) 强制 `since` 窗口（近 N 天）再排序，超窗走预计算。**注意**：spec 27 的"今日几十条"前提已被实测打破（近 24h 可读 3234 条），任何"窗口天然小"的假设不成立。
2. **前端侧**：行级 `memo` + 列表虚拟化（固定行高或用 `content-visibility`）；侧栏源数据与文章打开解耦（提升到 store，按 id 取投影，不再整表重拉）。
3. **传输侧**：`/api/sources` 支持 `?fields=` 轻投影（侧栏只需要 `id,name,avatar,type,group_id`），或前端改拉 `/api/sources/library` 的既有轻端点；`api.js` 的 5s TTL 策略要显式写出并对账。

## 判据与验收

- AC1 `sort=smart` 连跑 ≥5 次的 **P95 < 2s**（当前 17.6s 最差值）。口径必须是**页面自己发出的那次请求**，不是直连 curl 的漂亮数字（B73 的教训：同参数直连 5s，页面路径 15~26s）。
- AC2 点开一篇文章后的 Network 断言：不出现 `>100KB` 的 `/api/sources`；e2e 剧本里以"响应体积 + 条数"双读数记录。
- AC3 `npm run eval:e2e` 的 §3.5 性能预算项由"记录"升级为"超限判红"（若仍做不到稳定测量，就明确留在 KNOWN_GAPS，不许静默忽略）。
- AC4 F2P：性能类改动用"改前后同端点连跑对比表"出证，落 `docs/eval/f2p/`（并按 **B106** 的构造规则：比较基线要能真跑到，不许因缺文件而假红/假绿）。

## 边界

- 不改数据模型、不动采集链路。
- 不在本包解决排序"看起来同源扎堆"的观感（→ 36-7）。
- 不为跑分而砍功能（例如偷偷把 smart 换成 time）；若最终选择"降级为窗口内排序"，必须在文档与本 spec 里写明口径变化并让用户拍板。
