# 总 Spec v2：产品结构重设计——从「全量收件箱」到「策展优先」（2026-09-14 深化版）

> ⚠️ **状态：商讨稿 v2（等用户确认后按 mew-spec 拆分实施）。取代 v1 的"归置式"思路。**
> 用户洞察（本版出发点）：
> ① 新闻永远出不完且源数递增——**「全量时间线」这个产品形态本身就是错的**；
> ② 一个人打开阅读器只会象征性看看最新消息，**着重精读的是每日早报、我的早报、周刊**（AI 已筛好的策展内容）；
> ③ 打开阅读器 = 1500 源全量流 + 晚上 1 万+ 未读——信息过载造成阅读障碍；
> ④ 后台"操作别扭"：没有前端对照（要开两个页面）、源管理一进来就是 1500 行表格、几个板块只是改参数的独立 Tab。

---

## 1. 产品结构重设计：四层信息金字塔（核心）

按"用户每天实际投入的注意力"分层，**默认界面只暴露前三层**：

```
        ┌──────────────────────────────────────┐
  每天    │ L1 策展层（精读）——AI 已替你读完并评分     │  每日早报 ~30 条
  必看    │   每日早报 / 我的早报（订阅+画像）/ 周刊   │  我的早报 ~10-20 条
        └──────────────────────────────────────┘  周刊 20 条/周
        ┌──────────────────────────────────────┐
  随手    │ L2 脉搏层（扫一眼）——实时在发生什么        │  热点榜时间流
  扫一眼   │   热点榜（自有源高分流 + 热搜子视图）      │  每天几十条、扫标题
        └──────────────────────────────────────┘
        ┌──────────────────────────────────────┐
  按需    │ L3 检索层（工具）——我想查某个源/关键词时才用 │  阅读器「检索模式」
  检索    │   阅读器 = 搜索 + 按源/分组查看，不是信息流  │  无未读压力
        └──────────────────────────────────────┘
        ┌──────────────────────────────────────┐
  存档    │ L4 存档层——读过的都在，需要时翻             │  我的阅读 / 历史存档
        └──────────────────────────────────────┘
```

**关键产品决策：阅读器不再是"收件箱"。**
- 默认视图 = **「今日」**：只显示过去 24h 的内容，且排序 = 订阅源优先 + 六维分数，量级几十条。
- 未读数焦虑消除：侧栏未读只统计**近 3 天**（历史自动视为已读归档，L4 沉淀不变）——"未读 25096" 这种数字从此消失。
- 「全部」视图降级为**检索模式**：入口移到搜索框旁，明确标注"按需检索"，列表无限流、必须带筛选条件（源/分组/关键词/时间范围至少一个）。
- 早报是主入口：阅读器顶部放「今日早报摘要卡」（导语 + 头条 3 条 + 跳早报全文），点击 L1 内容不需要离开阅读器。

## 2. 源选择（A3 枢纽）在金字塔中的位置

用户"选择部分源"作用于**每一层**，但语义不同：
| 层 | 源选择的语义 |
|---|---|
| L1 早报 | 订阅集（早报中心管理，已有） |
| L2 热点榜 | 屏蔽集（不想在脉搏里看到的源/分组） |
| L3 检索器 | 视图模式（全部/聚焦/自定义勾选，上版方案保留） |
| 采集 | 全量照采（选择不减少采集——检索层随时可回看任何源） |

**这就是关联性**：一个选择器组件三处复用，但每层只暴露它该有的语义——
用户不需要理解 1500 源的全貌，只需要在各层做"我此刻想看什么"的决定。

## 3. 管理后台重设计：对照式管理（解决"操作别扭、开两个页面"）

### 3.1 对照原则（每条硬性）
- **C1** 每个 Tab 顶部放「它管理的前台页面」入口卡（前台页面名 + 一键跳转 + 当前生效配置摘要）。
- **C2** 每个设置项旁标注作用对象：`→ 阅读器排序` `→ 我的早报补充阅读` `→ 热点榜精选`。
- **C3** 后台内嵌前台实时预览：改动保存后，Tab 侧栏显示对应前台页面的关键数字变化（如"订阅集 8 源 → 明日我的早报预计覆盖 X 篇"）。

### 3.2 源管理改革：从「1500 行表格」到「以组为单位」
现状：进源库 = 一张 1446 行的表，管控压力巨大。
重构为三个视图（默认第一个）：
1. **组合视图（默认）**：以"组"为卡片单位——`AI·前沿 33源 | 正常率92% | 180min | [暂停组] [调频] [进入]`；
   顶部只显示**需要处理的组**（含熔断源的组排前）。
2. **问题源视图**：只列熔断/报错/新增未确认的源（日常真正要管的就这几十个）。
3. **检索视图**：搜索/筛选后才出现表格（现表格整体移入此视图）。
- 组级操作：整组暂停/恢复、整组调频、整组 failoverGroup 标记（配合 T4-2）。
- 单源操作保留在「进入组」后的列表里。

### 3.3 参数型板块合并
"只改几个参数"的板块不再是独立 Tab：
- 「AI 能力」+「翻译 Skill」→ **「AI 能力」单 Tab**（配置 + 翻译队列观测两区块）。
- 「数据」+「监控」+「报警管理」→ **「系统」单 Tab**（三区块：数据/饼图、监控/折线、报警/时间线——图表已就绪，只动容器）。
- 最终后台 Tab：**源库 / 早报中心 / 热点榜策展 / AI 能力 / 系统**（5 个）。

## 4. 数据流与关联性总图（架构层）

```
                    ┌──────────── 采集层（不变）────────────┐
                    │ 1446 源 → runner 15min → 六维评分入库  │
                    └───────────────┬──────────────────────┘
                                    │ articles/videos（score/reason/tags）
      用户选择 ──┐                   │
      （订阅集/  │                   ▼
      聚焦/屏蔽）├──► L1 早报管线（初筛→深析→主题/栏目）──► daily_reports / mybrief
                ├──► L2 热点榜（score≥阈值时间流 + 热榜聚合子视图）──► /api/hot
                ├──► L3 检索器（view 参数服务端过滤）──► /api/articles
                └──► L4 存档（我的阅读，不变）
      画像（reading 行为）──► L1 排序加权 + Domain 配额（已上线）
```

**职责边界（回答"他们怎么关联性才强"）**：
- 采集层永远全量（检索层保证可回看）；
- 用户选择**只过滤消费端、永不删除数据**；
- 评分是唯一的跨层排序货币（一处评分，处处生效）；
- 每个消费端声明自己消费哪些枢纽字段（在 spec 与界面标注中体现）。

## 6. 边界与风险

- 阅读器默认视图变更会改变老用户习惯——保留「全部」入口（检索模式），不删功能只降级入口。
- 未读口径变化需一次性数据迁移说明（历史未读自动归档，存档层不变）。
- 播客播放依赖 RSS enclosure 字段（68 源 feed 均为标准播客 RSS，可行）；YouTube 播放走外链/嵌入（国内可达性待观察，不行则仅外链）。
