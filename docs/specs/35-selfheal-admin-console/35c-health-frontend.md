# 35C · 源健康度与自愈的前端呈现 Spec

> 总框架：`spec.md`。状态：**待批准，未动工**。依赖 35A（自愈事件）+ 35B（成功率真值）。
> 关联现状代码：`web/src/components/SourceLibraryTab.jsx:33-37`（`healthStatus()`）、`:389/:409`（问题源视图）、`:567/:618`（检索视图）、`web/src/components/SourceTable.jsx:10-18`（重复实现）、`web/src/components/MonitorTab.jsx:8-11`（`rateColor()`）、`:111-151`（成功率表，颜色当前失效）、`web/src/index.css:73-82`（主题文字色）、`:398-406`（`.badge-red`）
> 最后更新：2026-09-18

## 背景

- 用户诉求原话：「每个源都要打上成功抓取概率，用数学公式表明概览，**最后前端只呈现重点颜色的百分比数字，问题比较大的源用红色**。」——即：要的是一个能扫读的彩色数字，不是一堆图表。
- 现状已经有一半：`MonitorTab.jsx` 有「源抓取成功率」表和 `rateColor()` 分档，但**它引用的 `t-success`/`t-warn`/`t-danger` 三个类在 `index.css` 从未定义**，所以颜色一直是坏的（ISSUES B22）。同一份"状态→颜色"逻辑还存在两处互不相同的实现（`SourceLibraryTab.healthStatus()` 与 `SourceTable.StatusBadge`），改一处必然漂移。

## 目标

- G1：源列表每一行有一个**可扫读**的成功率数字，颜色即结论，不需 hover 才懂。
- G2：坏源一眼捞出（按成功率排序/筛选），支撑 35A 的"哪些还在冷却、哪些真死待人工"。
- G3：颜色与阈值只有一处定义，三处 UI 共用。
- G4：数据不足时明确表达"不知道"，不用 0% 或 100% 冒充。

## 功能需求

- **F1 单一色彩函数**：一个「成功率 → 颜色档」的唯一实现，输入 35B 的 `p̂` 与 `W`，输出档位（含"未知"）。默认分档：
  `p̂ ≥ 95` 绿 · `80–94` 青/中性偏绿 · `50–79` 橙 · `< 50` **红** · `W < Wmin` 灰「—」。
  阈值可配（`settings.healthThresholds`），但同一份配置必须被所有视图读到。
- **F2 源列表呈现**：阅读器侧不显示（读者不需要），**管理后台源库三视图 + 问题源视图**统一改为「彩色百分比数字 + 极小样本量标注」，替换现有三态徽标；旧徽标保留在 tooltip/详情里。
- **F3 重复实现收敛**：`SourceTable.StatusBadge` 与 `SourceLibraryTab.healthStatus()` 合并到一个组件（`RateBadge`），两处调用点各自替换；不留第二份色彩逻辑。
- **F4 修坏掉的颜色**：`MonitorTab.rateColor()` 用到的文字色必须在三主题（亮/暗/第三主题）下都有定义，走现有 CSS 变量体系（`--green`/`--red`/`--accent`/`--surface-2`），**禁止新造色值**；红档统一用 `.badge-red` 同源色。
- **F5 冷却与自愈可见**：后台展示 35A 的事件流——「今日系统自动恢复 N 个 / 冷却中 M 个 / 判定真死待人工 K 个」，每行给源、类别、上次自愈时间。这是让用户敢放手的前提：不显示的话，自动恢复看起来像"源自己好了又自己坏了"。
- **F6 排序与筛选**：源库支持按成功率升序、按"红档/未知/冷却中"筛选（服务运维视角；用户日常只看红）。
- **F7 口径自解释**：数字旁一次说明（页脚或帮助浮层）给出公式与分档，避免"这个 75% 是啥意思"反复问；文案与 35B-F3 保持同源，不各写一份。
- **F8 懒加载一致性**：后台 Tab 骨架屏（B11 在途改动）与本板块新增面板同语言，切 Tab 不出现空白闪。

## 非功能需求

- **N1 零额外请求**：成功率必须搭 `/api/sources`（或既有 `/api/health/source-stats`）一次返回，前端不为每行发请求。
- **N2 感知性能**：1400+ 源列表在筛选/排序下不卡（现有列表已是虚拟/渐进渲染的语境，不得引入 O(n²) 重排）。
- **N3 三主题与可读性**：三种主题下红/橙/绿的对比度都要过无障碍最低档（灰「—」不许与正文同色以致看不出）。
- **N4 移动端**：安卓手机看后台时数字不被挤没（本项目设备事实：Windows 开发 + 安卓查看）。
- **N5 无 JS 报错**：新面板在数据缺失（后端未上 35B）时降级显示「—」，不得抛错白屏（沿用 `ErrorBoundary`）。

## 不做的事

- 不做图表大屏/趋势曲线/热力图（用户要"只呈现重点颜色的百分比数字"）。
- 不做前端本地计算成功率（口径必须在后端，避免三端各算一套）。
- 不改后台整体信息架构与 Tab 布局（属 35D，最低优先级）。
- 不给读者端页面加任何健康度元素。
- 不做"综合健康分"或把成功率与 AI 评分揉一起。

## 验收标准

- **AC1（F1/F4）**：构造 `p̂`=98/88/63/22 与 `W` 不足五种数据，截图断言颜色与预期一致，三主题各一遍；`t-*` 类在 `index.css` 中确有定义（B22 关闭）。
- **AC2（F2）**：源库三视图 + 问题源视图四处调用点全部换成 `RateBadge`，`grep` 断言不再存在第二套状态→颜色映射。
- **AC3（F3）**：`SourceTable.StatusBadge` 旧实现被删除或改为转调 `RateBadge`（不留双份）。
- **AC4（F5）**：后台能看到当日自愈事件流，条数与 35A-F7 记录一致（与 DB 直查对照）。
- **AC5（N1）**：Network 面板确认打开源库时**没有**逐行请求；单次请求返回体增量 <20KB。
- **AC6（端到端）**：登录后台 → 源库按成功率升序 → 第一个红档源点进去能看到失败类别与最近自愈记录 → 人工"立即重试"能触发一次真实探活并改变数字。
