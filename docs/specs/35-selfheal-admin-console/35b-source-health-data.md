# 35B · 源抓取健康度数据地基与成功率公式 Spec

> 总框架：`spec.md`。状态：**待批准，未动工**。mew-spec 阶段一（做什么）。
> 关联现状代码：`api/[...slug].js:1693-1704`（假成功率）、`tools/collect-turso.js:489-505`（`settings.cloud.collect` 心跳）、`:399/408`（成功清零 / 失败 +1）、`lib/collectors/fetcher.js:47`、`server/services/collectors/store.js:21-35`
> 最后更新：2026-09-18

## 背景

用户要「每个源打上成功抓取概率，用数学公式表明概览，前端只呈现彩色百分比，问题大的源红色」。

现在给不出这个数：

| 可用信号 | 实际语义 | 能不能当分母 |
|---|---|---|
| `sources.fail_count` | **当前连续**失败长度，成功即清零 | ❌ 无分母（一次成功就回到 0） |
| `sources.status` | 最后一次的结果 | ❌ 布尔 |
| `extra.lastErrorAt/frozenAt/resumeCount` | 负样本事件，且 `frozenAt` 会被恢复逻辑重置 | ❌ 只有失败面 |
| `settings.cloud.collect.history` | 批次级 `{total,success,failed}`，**failures 截断 20 条且只含失败源**；窗口实测只有 **25 小时**（代码注释写「7天」是错的） | ⚠️ 全局批次真概率可以，**逐源不行** |
| `articles` 出文密度 | 分不清「抓失败」和「源没更新」，且 7 天保留期在删 | ❌ |
| `static-data/sources.json` 快照 | 只含 `enabled=1` 的日频点采样 | ❌ |
| `job_queue`（本地） | 云端 2571 行全是 09-05~09-07 迁移死数据 | ❌ |

结论：**必须先补"每次尝试"的留痕**，否则任何百分比都是装饰。云端现状 `rate: status==='ok'?100:0` 属于用布尔伪装概率，比不显示更糟。

## 目标

- G1：每个源都有一个**由真实分母算出**的成功率，数据不足时明确显示「未知」而不是 100%。
- G2：成功率能区分「源坏了」与「源没更新」——后者不是病。
- G3：成本可控：不为此把 Turso 撑爆（本地/云端同构）。
- G4：这个数字同时是 35A 自愈的输入（冷却决策看同一份窗口，不另建一套）。

## 功能需求

- **F1 三态尝试记录**：每一次"到期并被尝试抓取"记一次结果为三态之一：
  `ok-new`（抓到且有新条目入库）、`ok-empty`（抓取与解析成功但无新内容——源安静，不是坏）、`fail`（网络/HTTP/解析失败，并带 35A-F1 的错误类别）。
  `skipped`（未到期、failover 备源让位、本地地址在云端不可达）**不计入分母**。
- **F2 每源滚动窗口**：每个源保留最近 N 次尝试的三态序列（默认 N=40）与错误类别计数，作为成功率唯一数据源。窗口长度、半衰期、N 下限可配。
- **F3 成功率公式（写进文档与接口，前后端同一实现）**：
  1. 时间衰减权重：第 i 次尝试距今 `Δi` 小时，权重 `wi = 0.5^(Δi / H)`，半衰期 `H` 默认 48 小时；
  2. 加权计数：`W = Σ wi`，`S = Σ wi · si`，其中 `si`：`ok-new`=1，`ok-empty`=`e`（默认 0.6，可调 0.5~1），`fail`=0；
  3. Beta 平滑（Laplace 一般式）：
     **`p̂ = (α + S) / (α + β + W)`**，默认先验 `α=β=2`（等价"先验 4 次、成功率 50%"，避免 2 次就打出 100%/0%）；
  4. 可信度门槛：`W < Wmin`（默认 3，即有效样本不足 3 轮）**不显示数字**，返回 `null` → 前端「—」；
  5. 输出附带 `W`（样本量）与主导失败类别，供 tooltip 与筛选使用。
  直觉示例：一个源窗口内 8 次尝试 = 7 次 `ok-new` + 1 次 `fail`（忽略衰减）→ `p̂=(2+7)/(2+2+8)=75%`；若其中 1 次成功其实是 `ok-empty`（`e=0.6`）→ `S=6.4` → `70%`；同一批尝试若发生在 5 天前，权重 `W` 变小、先验占比变大，数字会向 50% 回拉（这就是「很久没采到样本」不该显示高分的原因）。
- **F4 派生指标**：同窗口顺带产出「连续失败长度」「上次成功距今」「本周被自愈次数」，用于 35A 冷却与 35C 排序，不合成单一"综合分"。
- **F5 三端写入口一致**：本地调度器、Vercel 手动采集、runner 三处采集成功/失败落库时都必须写同一窗口；判定与计算函数唯一实现落 `lib/`（同 `lib/source-axes.js` 模式）。
- **F6 只读接口**：`/api/health/source-stats` 改为返回真值（含 `W`、类别、`unknown` 标记），保留旧字段一个周期以兼容前端；提供按成功率/失败类别筛选源列表的查询参数。
- **F7 保留与回收**：窗口是定长滚动，不增长；错误类别计数随窗口滑出自动过期。**不新建大表**（理由见 N2）。

## 非功能需求

- **N1 体积**：新增字段不得让 `sources` 行显著膨胀（目标：每源 <120 字节；1437 源合计 <200KB）。
- **N2 为什么不用流水表**：实测每轮约 410 个源被尝试、每天 96 轮 → ≈4 万行/天，30 天保留即 120 万行。为算一个 40 轮窗口的成功率付这个代价不划算；滚动窗口数学上等价（公式只吃最近 N 次），故本板块选窗口。**放弃的是**：超过窗口的历史回溯、任意时间轴趋势图——列入「不做」。
- **N3 读放大**：成功率必须在**写入时**折算成标量存下（或批次内预算），禁止在 `/api/sources` 每次请求里对 1400 源重算公式（Vercel 30s 预算 + 慢性 504 面，同 H11 教训）。
- **N4 一致性**：`ok-empty` 的权重 `e` 改动会影响全体数字，必须版本化（记录在 `settings` 里，接口回显口径），避免新旧数字混排无法解释。
- **N5 隐私/安全**：错误类别不得携带密钥或完整 URL query（复用 `log.mask` 语义）。
- **N6 可测**：给定窗口序列，公式输出必须可在单元测试里精确断言（含衰减、平滑、`unknown` 三态）。

## 不做的事

- 不做历史趋势报表 / SLA 看板 / 任意时间轴回溯（窗口之外无数据）。
- 不做"综合健康分"（把成功率、出文量、AI 分数揉成一个数）——用户要的是成功率，揉分只会不可解释。
- 不改数据保留策略本身（`settings.data.retentionDays` 维持现状）。
- 不做跨源对比排名可视化、不做告警阈值以外的自动决策（自动决策属 35A）。
- 不在本板块改前端布局（属 35C）。

## 验收标准

- **AC1（F3）**：用构造的窗口序列断言公式：①全成功 → 接近但不等于 100%（受 `e` 与先验影响）；②`ok-empty` 为主的安静源 **不得**被判红档；③样本不足 → 返回 `null` 而非 0/100。
- **AC2（F1）**：抓取失败、抓取成功但无新内容、未到期跳过三种情形各跑一次，断言只有前两种进分母。
- **AC3（F2/F5）**：三端各跑一轮真实/模拟采集，同源代码写的窗口结构一致；跨端回归测试通过。
- **AC4（N3）**：`/api/sources` 响应耗时不因新增字段明显上升（实测：与改前对比 <10% 增幅），且代码里不存在"每请求重算 1400 源公式"的路径。
- **AC5（F6）**：`/api/health/source-stats` 不再出现 `status==='ok'?100:0` 形态；对 20 个真实源抽样，数字与手工按公式核算一致。
- **AC6（真实世界）**：上线 24h 后，云端 210 个熔断源对应的成功率呈红档、而"源安静"类源呈绿/中档（人眼抽查 10 个），且不存在 100%/0% 两极分布占绝大多数的假数据形态。
