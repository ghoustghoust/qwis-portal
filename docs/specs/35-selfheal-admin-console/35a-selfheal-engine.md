# 35A · 采集自愈引擎 Spec

> 总框架：`spec.md`（同目录）。状态：**待批准，未动工**。mew-spec 阶段一（做什么）。
> 关联现状代码：`tools/collect-turso.js:404-423`（熔断判定）、`:697-720`（48h 自动恢复）、`server/services/collectors/store.js:19-58`（本地只熔断不恢复）、`api/[...slug].js:1596-1627`（人工解冻端点）
> 最后更新：2026-09-18

## 背景

系统已经有"熔断"，但没有"自愈"：

- 熔断太容易：3 次连跪（YouTube 10 次）就 `enabled=0`，而一次网络抖动、一次代理挂掉、一次桥抽风都会连跪。实测 **18/23 抽样源重试即成功**，说明熔断群体里绝大多数不是死源。
- 恢复太慢且一刀切：云端要等 **48 小时**、每天只有一次 cleanup 机会（实际 48~72h），第 4 次直接流放 **7 天**；本地端**根本没有**自动恢复。
- 不看错误性质：假 404（YouTube 反爬掷骰）、`fetch failed`（本机代理/出口故障）、`SERVER_ERROR 400`（xgo 桥）、`value.toString is not a function`（**我们自己的解析器 bug**，实测 11 个源）与真失效 410 全部同等处理。
- 最坏的一次：2026-09-13T03 一次代理故障，本地 **458 个源在同一小时被批量熔断**，至今全部锁死。

用户诉求原话：「这些工作其实根本用不上人，只需要出错后过一会重启就能解决。」——实测成立（78% 重试即恢复），故本板块目标是**把"过一会重试"做成系统行为**，而不是把"手动点按钮"做得更顺手。

## 目标

- G1：瞬时故障不再导致长时间不可用；用户不再需要为了"其实没坏的源"登录后台逐个点。
- G2：真死源仍然要被隔离并让人看见——自愈不许把问题藏起来。
- G3：每一次自动恢复/延长冷却都可追溯（谁、什么时候、为什么、结果如何）。
- G4：系统性故障（代理/桥/网络出口）不折算成单源失败。

## 功能需求

- **F1 故障分类**：每次采集失败必须归入一类，且分类驱动后续动作。至少区分：
  `transient-network`（超时/连接失败/DNS）、`external-block`（403/429/假 404/Cloudflare 挑战页）、`bridge-down`（RSSHub/wechat2rss/xgo/本地 we-mp-rss 不可达）、`parser-defect`（我方解析异常，如 `value.toString`、`Attribute without value`、非法实体）、`gone`（持续 404/410 且重试仍 404/410）、`unknown`。
  分类结果必须落库可查（现 `api/_alerts.js:classifyError` 已有雏形，本板块要求它成为**决策输入**而非仅报警文案）。
- **F2 退避重试代替立即锁死**：未达熔断前，按错误类别用递增间隔重试（如 15min→30min→1h→2h 封顶），而不是同节奏硬撞 3 次就锁。计数与窗口可配。
- **F3 解冻前探活（probe-first）**：任何自动恢复动作之前，先发一次真实轻量请求验证源可用；探活成功才 `enabled=1` 并清零，探活失败则按类别延长冷却（而不是无条件放回）。
- **F4 分级冷却**：冷却时长由类别决定，而不是由"连跪次数"单一决定。基线：`transient-network`/`external-block`/`bridge-down` 分钟级~小时级；`parser-defect` **不熔断**（是我们的 bug，锁源等于把问题藏起来，只报警 + 标记）；`gone` 才进入长冷却与"待人工处置"队列。
- **F5 本地端补齐**：本地调度器必须具备与云端同一条恢复链路（当前为零）。恢复逻辑唯一实现落 `lib/`，三端引用，避免再次分叉。
- **F6 系统性故障抑制**：单轮内失败率超过阈值（默认 ≥30% 到期源失败，或失败错误指纹高度同源，如 458 个源同一小时同样 `fetch failed`）→ 判为基础设施故障：本轮**不增加任何源的 fail_count、不熔断**，只发一条"出口/代理疑似故障"报警，并把本轮标记为 degraded。
- **F7 自愈留痕**：每次自动恢复/延长冷却/抑制熔断写一条结构化记录（源、时间、前态、触发类别、动作、结果），后台可见、可查询、有保留期。
- **F8 后台呈现自愈动作**：管理后台「监控/系统」处能看到"今天系统自己救回了多少源、哪些还在冷却、哪些判为真死待人工"，并保留现有人工批量入口作为兜底（改造 `restore-all`：**按类别分批试探恢复**而非无差别解冻，见 `docs/ISSUES.md` H15）。
- **F9 报警协同**：自愈成功不打扰用户（进汇总），自愈连续失败 N 次或判为 `gone` 必须报警；现有 `frozenDigest()` 保留并升级为"日自愈汇总"。

## 非功能需求

- **N1 三端一致**：分类、退避、探活、冷却的判定函数只允许一份实现（`lib/`），`server/`、`api/`、`tools/collect-turso.js` 三端引用；改动必须有跨端回归测试。
- **N2 云端预算**：读层函数 30s 内不得做探活（外网请求一律在 runner）；Vercel 端只提供状态读取与人工兜底入口。
- **N3 不放大攻击面**：探活仅对库内已登记 URL 发起，禁止用户可控输入拼进 URL（防 SSRF，见 H3）。
- **N4 幂等与安全**：自愈动作不得覆盖人工设置（用户手动禁用/退役/合并的源永不被自动放回）；`mergedInto`/`retired` 判据沿用现实现。
- **N5 可回退**：整套自愈挂配置开关（默认开），出现误判时可一键退回"只熔断不自愈"的当前行为。
- **N6 零副作用可测**：必须能在测试里用假 fetch/假时钟驱动完整状态机，不依赖真实外网。

## 不做的事

- 不自动删除源、不改 URL、不换桥、不做内容级质量判断。
- 不试图"解决" YouTube 数据中心 IP 反爬（那是 H1 挂案，需住宅代理）。
- 不引入外部调度/监控栈，不做多机分布式锁。
- 不做"预测性熔断"（源还没坏就提前停用）。
- 不在本板块动管理后台页面布局（属 35D）。

## 验收标准

- **AC1（F1/F4）**：给 6 类假失败各造一个源，跑一轮采集，断言：只有 `gone` 进入冷却队列；`parser-defect` 不改变 `enabled`；其余按类别进入分钟/小时级冷却。
- **AC2（F2）**：单源连跪 3 次期间，其 `next_fetch_at` 间隔序列单调递增且不触发 `enabled=0`（基线行为是第 3 次即锁）。
- **AC3（F3）**：冷却到期时探活失败 → 不恢复、冷却延长并写记录；探活成功 → 恢复且 `fail_count` 归零。
- **AC4（F5/本地）**：本地端把一个源置为熔断，24h 模拟时钟内无人为操作，该源自动恢复；当前行为（永不恢复）必须有回归测试锁死差异。
- **AC5（F6）**：模拟一轮 100% 失败（同一错误指纹），断言 0 个源 `enabled` 或 `fail_count` 变化，且产生一条"疑似出口故障"事件。
- **AC6（F7）**：后台可列出最近自愈记录（源、时间、类别、动作、结果），保留期内可查。
- **AC7（真实世界）**：修复上线后 24h 实测——云端 `enabled=0 AND status='error'` 存量从 210 降到 <30，且本地 584 个历史锁死源被一次性分批试探恢复后不留残骸（证据：`/api/health/source-stats` + Turso 直查）。
- **AC8（N1）**：三端语义回归测试存在且通过；`npm test` 不新增红。
