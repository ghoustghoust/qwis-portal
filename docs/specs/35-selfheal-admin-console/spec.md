## 1. 背景：为什么现在必须做

### 1.1 实测证据（2026-09-18 只读评测，脚本已删，可复现）

用户判断：「很多问题（采集失败、自我熔断、YouTube 容易挂）非要等用户登录管理后台手动一个一个点重启；源并没有彻底损坏，出错后过一会重启就能解决，这些工作根本用不上人。**你去测。**」

测出来的结论——**方向对，归因要改**：

| 线 | 事实 | 证据 |
|---|---|---|
| **云端 runner** | 自动恢复**存在且在工作**（最近一轮 cleanup 一次恢复 66 个源；45 个源 `resumeCount>=1` 至今正常出流） | `tools/collect-turso.js:697-720`、`settings.cloud.collect` history |
| 云端真问题 | 恢复等待 **48h 起步**（`resumeCount>=3` 直接 7 天），而熔断只需 **45min**（3 连跪 × 15min 节奏，`:415`）→ 「恢复→中位 6.2h 后再锁→再等 48h」死循环，用户等不到只能手动点 | 195/210 熔断源 `lastErrorAt > frozenAt`；`frozenAt` 精确聚集在每天 cleanup 那一小时（09-14/15/16/17 各一批） |
| **本地端** | 用户**完全正确**：584 个熔断源**零自动恢复路径**，已锁 5~7 天，不点就永远不恢复 | `server/services/collectors/store.js:31-38` 只置 `enabled=0`；`scheduler/jobs/maintenance.js` healthCheck 只报警不恢复；恢复入口全是手动（`routes/health.js:87,104`、`routes/restore-all.js`） |
| 「其实没坏」量化 | 分层抽样 23 个熔断源真发重试：**18 个（78%）立刻成功**（含 6 个 YouTube 假 404、3 个 xgo 桥 400、2 个 403、1 个解析器 bug）；仍失败 5 个里 3 个是桥侧/反爬（退避可解）、1 个 feed 真变、1 个需 Cookie | 代理 127.0.0.1:12000 + `undici.fetch`（与 runner 同写法） |
| 最严重的误判 | 本地 458 个源的 `lastErrorAt` **全落在 2026-09-13T03 同一小时**，错误一律 `fetch failed` = **一次代理故障把整库批量熔断**，且永远没恢复 | `data/app.db` 只读查询 |

**当前存量（2026-09-18T14:46Z）**：云端熔断 210（youtube 100 / rss 67 / x 39 / hotlist 3 / bilibili 1），其中 126 个已过 48h、今晚 cleanup 会被自动恢复；本地熔断 584，全部永不恢复。

### 1.2 「源成功率」的现状是假数据

- 云端 `/api/health/source-stats`（`api/[...slug].js:1693-1704`）注释自陈「云端无 job_queue 历史」→ 实现是 `rate: status==='ok' ? 100 : 0`。**这是布尔伪装成百分比**，不是概率。
- 前端 `MonitorTab.jsx:111-151` 已经有一张「源抓取成功率」表和 `rateColor()` 分档，**但它用的 `t-success/t-warn/t-danger` 三个 CSS 变量在 `web/src/index.css` 根本没定义** → 颜色永远不生效（本轮检测新问题，见 ISSUES B22）。
- 真概率缺分母：全库唯一流水 `settings.cloud.collect.history` 只留 168 条 ≈ **25 小时**（代码注释写「7天」是错的），且 `failures[]` **截断 20 条、只含失败源** → 有负样本无正样本，逐源算不出可信分母。

| 板块 | 小 spec | 解决什么 | 规模 | 前置 | 优先级 |

| **A 自愈引擎** | `35a-selfheal-engine.md` | 熔断不再靠人点：分类→退避→探活→自动恢复→留痕 | 中（三端语义） | 无 | **A1** |
| **B 健康度数据地基** | `35b-source-health-data.md` | 每源每次 attempt 留痕，成功率才有分母 | 中（含 schema） | 无 | **A2**（与 A 并行） |

拆分理由：A/B 无相互依赖可并行；C 依赖 A 的自愈事件与 B 的分母；D 是页面骨架层，放在数据与行为稳定之后，避免「边改数据模型边改布局」。

## 3. 全局边界（四个板块共同遵守）

**必须**
1. 采集/熔断/恢复语义**三份实现同步**（`server/services/collectors/`、`api/collect.js`、`tools/collect-turso.js`）——AGENTS §1 铁律；本轮实测已证明三份不一致会让「同一个源在本地永不恢复、在云端 48h 后恢复」。唯一实现优先落 `lib/`（同 `lib/brief-guards.js`、`lib/source-axes.js` 模式），三端引用。
2. 不引入无头浏览器、不引入需要本地文件系统的云端功能（不动刀原则 §2.7）。
3. Vercel 读层 30s / runner 单轮预算内完成；重活一律放 runner，读层只做投影。
4. 自愈必须**可观测**：每一次自动恢复/延长冷却都留一条结构化记录并在后台可见——否则用户看到的是"源自己好了又自己坏了"，比手动点更不可信。
5. 报警不许被自愈刷屏（合并 + 冷却），也不许被自愈吞掉（真死源必须继续报）。

**不做**
- 不自动删除/退役源，不改源 URL，不自动换桥（这些保留人工决策）。
- 不做「全自动无人值守且无日志」的黑盒自愈。
- 不在本轮解决 YouTube 数据中心 IP 反爬本身（H1 挂案，需住宅代理）；只做「按错误类型区别对待，不要把抖动当死亡」。
- 不为成功率引入外部监控栈（Prometheus/Grafana 等）。

## 4. 验收总口径（板块级；细则见各小 spec）

- AC0-1：本地端熔断源在无人干预下 24h 内自动恢复率 ≥ 95%（当前 0%）。
- AC0-2：云端「瞬时抖动型」熔断源（重试即成功类，当前占 78%）平均不可用时长从 **48~72h** 降到 **≤ 1 小时**。
- AC0-3：一次代理/桥故障不再批量熔断（模拟 1 轮 100% 失败，结果：0 个源 `enabled` 变化）。
- AC0-4：后台每个源显示一个彩色百分比，且该数字**由真实 attempt 分母算出**（禁止 100/0 伪装）；数据不足时显示「—」而非 100%。
- AC0-5：`npm test` 不新增红 + `npm run build:vercel` 无错 + 云端实测（`docs/DELIVERY_VERIFICATION.md`）通过 + 文档按 `docs/DOC_GOVERNANCE.md` 同步归档。
