## 背景：这一块的风险等级和其他板块不一样

清理与恢复是**不可逆动作**。本轮在这里修掉的两个坑都属"界面把状态说错"：

- **B54**：保留天数藏在"执行清理"的成功分支里才 `PUT /api/settings` —— 设置成了清理的副作用，改了不保存。已拆独立 `saveRetention` + 按钮态显示"已保存 / 有未保存改动"。
- **B56**：云端不提供文件快照，界面却显示"暂无快照"（听起来像"还没生成"）。已改为**布尔能力位** `fileSnapshots`（云端 false / 本地 true），先判能力位再判列表长度，不支持时禁用按钮并写"本部署不提供该能力"（坑 #38）。
- **B55 仍在**：后台清理用 `COALESCE(published_at, created_at)`，runner 清理只看 `published_at` → 同一份"保留 N 天"在两处算出不同集合。**两个删除器口径不一致，比没有删除器更危险**（谁跑谁赢，且没人知道自己赢了什么）。
- **BL10 待授权**：`read_at='null'`（字符串）污染 2.5 万行，直接毒害"保留清理豁免 / 未读角标 / 阅读足迹"三处口径 —— 用户决定"先不写生产，等评测就位"，故本板块任何清理相关的验收都必须显式声明"数字含已知污染"。

## 边界

- 本板块不做监控读数（→ 38-G），不配置 AI（→ 38-E）。
- **写库的破坏性动作一律要预览 + 确认 + 回读校验**三件套；缺任何一件视为未实现（这是本轮 B47/B54 的共同教训：读数错和副作用式保存都源于"没有回读"）。
- 不在本板块修 BL10 的数据 —— 那需要用户授权（"先不写生产"）。

## 验收标准

- AC1：F2 —— 后台清理与 runner 清理对同一份库算出的"待删集合"**逐条相等**（回归锁：同一 SQL 生成器，两侧引用；配 diff 测试）。
- AC2：F3 —— 预览请求与执行请求的条数一致（不一致即拒绝执行并报错）。
- AC3：F4 —— 云端实测：快照区无"暂无快照"字样、按钮 `disabled`（本轮已有锁 B56-0/1/2，端到端复跑）。
- AC4：`npm run eval:whitebox` 不新增"同一判定第二份"缺口（W10 直接盯 F2 这种口径分叉）。
