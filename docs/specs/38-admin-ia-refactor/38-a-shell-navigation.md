## 背景：壳的问题会让每个板块都变贵

实测的三件硬伤（定量见 `spec.md` 背景表）：

1. **左缘永久错位 54px / 70px**（B35）：header 内层 `max-w-[1100px]` 且 padding 在内（`AdminPage.jsx:56-57`），main 的 padding 在外、内容宽 1160/960（`:83-84`）。这不是审美：任何板块想加"对齐的两列布局"都会撞上它，于是每个板块各自就地补 margin → 越补越乱。
2. **刷新即丢位置**（B37）：Tab 态是 `useState`，`/admin` 永远回到源库。用户排障时"跳到报警台→被 Vercel 日志分散→回来"要重新点三层；板块拆得再细也救不了这个。
3. **保存语义三套并存**（B36）：BriefCenter/Hot/Alerts/Data 即时写、DailySettings 四区共用底部一个按钮、AiSettings 两个按钮；全库无 dirty 未保存提示（grep 零命中）。同一个后台里"改完要不要点保存"没有一致答案 = 用户必须逐个板块重新学一遍。

外加 B38（同一页重复请求 `/api/settings`）与 B25（上一轮中断留下的在途改动未提交，改这个文件会撞车）。

## 目标

- 一个板块 = 一个可寻址的路由；壳只负责"路由 ↔ 板块"，不掺任何业务判断。
- 保存模型全后台二选一并写进规范：要么**全即时写 + 显式"已保存"**，要么**草稿 + sticky 保存条 + dirty 提示**。不许并存。

## 边界

- **不拥有任何 settings 键**：壳只跳转，写键一律发生在业务板块。
- 不引入新 UI 库（沿用 Tailwind + 三主题 CSS 变量）；不动读者端页面。
- **顺序约束**：A1/A2 的深链键（路由名）必须一次定好，38-B~38-H 的"跳转到板块"全依赖它——所以本板块是 38 域里唯一**建议先做**的一块（工作包 38-3）。

## 验收标准

- AC1：5 个板块深链可直达，刷新不回源库（Playwright 剧本，spec 41 §3）。
- AC2：A3~A6 各自的 grep/量像素判据全过；`npm run eval:whitebox` 不新增缺口（W10 会盯"同一判定被抄第二份"，路由名同理）。
- AC3：任一板块的"未保存"状态在切走时被拦截（不许静默丢改动）。
- AC4：本轮修过的 B22 颜色变量在三种主题下仍正确（回归锁已有）。
