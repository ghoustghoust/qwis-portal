# 05 - 任务队列选型决策

> 类型：已确定（短期不变）
> 生效日期：2026-09-05
> 决策人：架构重构计划

## 背景

重构 Phase 5 需要引入任务队列替代当前 setInterval + 串行 await 的 tick 机制。需要选择队列实现方案。

## 选项对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| Redis + Bull/BeeQueue | 成熟稳定、分布式支持 | 引入外部依赖、PM2 单 fork 用不上分布式特性 |
| 内存队列（async-await 池） | 零依赖 | 进程重启丢失任务、无持久化 |
| **SQLite job_queue 表** | 零新依赖、持久化、WAL 模式已启用 | 非标准队列中间件 |

## 最终选择

**SQLite-backed TaskQueue**：用已有的 better-sqlite3 + job_queue 表实现，不引入 Redis。

## 理由

1. 项目哲学自包含（PM2 单 fork，不需要分布式队列）
2. 已有 SQLite 连接 + WAL 模式，无额外依赖
3. SQLite 持久化保证进程重启不丢任务
4. 写锁竞争不存在（WAL 模式 + 单进程）
5. 实现简单（~180 行），易维护

## 设计要点

- 并发 5，同源去重（perSourceLimit=1）
- 优先级排序（focus 源 100，普通 50）
- 崩溃恢复（启动时 running → pending）
- 重试策略（最多 3 次，failed → pending）
- 回退开关（QUEUE_ENABLED=false 回退串行模式）

## 影响范围

- scheduler/index.js tick() 改为 scanAndEnqueue() + taskQueue 消费
- 新增 job_queue 表（db.js DDL 迁移）
- 新增 tests/task-queue.test.js（9 个测试用例）
