## 原始需求

引入 k6（Grafana 开源负载测试工具）进行持续性能监控，替代当前 `tools/perf-check.js`（173 行简单健康检查）。

审计报告原文：
> "性能基准测试工具不完善。tools/perf-check.js 仅 173 行简单检测，缺少压力测试（ab/wrk/nginx ab），无 APM 埋点（JMX/NPM）。建议集成 k6 或 Artillery 进行持续性能监控。"

## 搁置理由

### 1. 项目规模不匹配

- **单用户本地/宝塔部署**：Express + SQLite 单进程，并发压力为零
- **无外部用户流量**：不需要 SLA 保障或性能基线监控
- **当前 `perf-check.js` 已足够**：覆盖服务存活检查、数据库连通性、关键路由响应

### 2. 实施成本高

- k6 需要安装 Go 二进制（~100MB）
- 需要编写 JS 负载脚本（定义场景、阈值、断言）
- 需要维护性能基线数据（P50/P90/P99 延迟、RPS）
- 需要 CI/CD 集成（GitHub Actions 定时运行）

### 3. 投入产出比极低

| 投入 | 收益 |
|------|------|
| 安装 k6 + 编写脚本 + 维护基线 ≈ 2-3 人天 | 单用户场景下几乎无性能瓶颈 |
| CI/CD 集成 ≈ 1 人天 | 已有 `perf-check.js` 覆盖基本健康 |
| 持续运行消耗计算资源 | 无外部用户，无性能退化风险 |

### 4. 当前性能状态

- Express 路由响应 <10ms（本地 SQLite 查询）
- 事件聚合引擎 <200ms（纯内存 Jaccard 聚类）
- 前端 Vite 构建 <5s
- 无已知性能瓶颈

## 未来启动指引

如项目演进到以下阶段，可重新评估：

1. **多用户/团队使用**：需要 SLA 保障时
2. **云端多实例部署**：需要容量规划时
3. **高频 API 调用**：需要限流/熔断验证时

启动步骤：
1. 安装 k6：`brew install k6`（macOS）或下载 Windows 二进制
2. 创建 `tests/performance/` 目录，编写场景脚本
3. 定义基线：P95 < 200ms，错误率 < 0.1%
4. 集成到 CI/CD：`.github/workflows/perf.yml`

## 替代方案

如仅需简单负载测试，可用：
- `autocannon`（Node.js 原生，无需额外安装）：`npx autocannon -c 10 -d 30 http://localhost:3000/api/health`
- 现有 `tools/perf-check.js` 已覆盖基本需求
