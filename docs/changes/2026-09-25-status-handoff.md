## 1. 做了什么（每条附"为什么是这一步"与实测读数）

### 1.1 用户改每源配额 → 真能改掉 → 早报覆盖的源数会变
这条线本轮接通了。改动前：这个设置项**代码一直在读，但后台写不进去**（只能直连数据库改），
所以"某个源今天有没有被看见"实际由运维手工决定。接通后：后台早报设置页有一格可填 → 保存写进配置存储 →
下一批早报生成时读到 → 该批"每源最多占几个坑"生效，前台表现为**入选源的数量变化**（不是总条数变化）。
每格有钳位（超出合法区间会被夹回，不会把批次打死），读接口会把**生效值**回显出来，避免"填了 100 实际跑 2"。

**但这"一次保存真的落库"至今没有被实测过**：只读探针查生产配置存储，**这一行根本不存在**
⇒ 生效值一直是默认值 2，也没有任何人真的在页面上保存过一次。原因不是坏了，是点保存就是生产写、我未授权。
所以现在这条链的证据形态是"读侧真回值 + 锁绿"，缺最后一段人眼与一次真写。

**为什么先做这条**：它是"宽池换覆盖"这个主张的唯一验证手段。没有可写的格子，任何一次覆盖改善都无法复现或回退。
**因果链已被真执行证明过一次**：同一批坑位下，两种配额跑出的入选源数量差是实测出来的，不是推算的。
最新两期的基线（宽池有多少源有货、500 个坑实际分给了多少个源）与"线上这一行至今不存在"的实测，
都记在 `docs/eval/2026-09-25-delivery-readouts.md`；本文件不复制这些读数（复制就会漂，且我这边还在复跑）。

### 1.2 初筛失败不再静默放行：九类原因落库 + 报警文案带头部原因
原来线上有一类失败是**完全看不见的**：某条内容送模型初筛，如果这一发调用失败，系统按"中位分"放行，
既不算通过也不算剔除，前台、降级标、报警里都看不出这批有多少是"没筛成"的。
实测规模：**500 条里 171 条 = 34.2%**（最新一期，只读探针直读生产库）。上一期是 10.8%；更早的 16 期**根本算不出来**——
不是没失败，是当时没存能算的字段。这张表本身就是"为什么要补字段"的答案。

现在失败会被归成九类（解析失败放行 / 模型只回思维链没正文 / 没配密钥 / 限流 / 服务端错 / 客户端错 / 超时 / 网络传输 / 其它），
每批汇总进当期统计，报警文本会带上占比最高的三类。**下一期开始就能判断该抬长度上限还是该加退避重试。**

**为什么不做成"失败即剔除"**：那是改变产品行为的一刀（会把模型没答的内容直接判死），需要你拍；本轮只让它可见。

### 1.3 主题全景：一簇要进库得连过六道出口，现在每道出口各自计数
"主题全景"多数期是空的，此前所有争论都指向"相似度阈值太严"。回放后发现阈值不是病根：
**放宽到很松，最大的簇仍然只有 2~3 条**，而库里十几期合计只存下 3 簇——中间掉下去的那些簇，没有任何一处留下"为什么掉"。
现在这六道出口分成两族各归各位：三处在**聚类之前**（样本太少、没共同词），三处在**命名阶段**（模型没答、没给出可解析的 JSON、答不全、格式坏），
每族都有可核对的守恒式（命名的结果数 + 四条命名出口的丢弃数 == 发起命名的簇数），并由两把锁钉住：
一把在源码层面盯"每个出口都必须计数"，一把在运行时真跑一遍生成脚本盯"计数对得上"。
锁的判据用**契约文件里声明的枚举**推导，不手抄清单——否则改一处枚举就会让锁和现实悄悄分家。

### 1.4 边界留了缓冲（你要求的"给各边界一些缓冲，我们有 9 小时"）
夜间批次的预算与作业超时都抬宽了，现在真实用量占总预算约三分之一上下（两期实测读数在 100 分钟量级 / 300 分钟预算）。
**同时登记了这条好意的副作用**：单批跑得更久，更容易撞上"上一次还在跑，这次的定时触发被丢弃"——
这笔收益和这笔风险必须一起观察，所以它挂在 H27（定时投递）名下，而不是只记在预算表里。

### 1.5 源侧：只量化，一个源都没动（你要的"细致查看问题"先建底稿）
读数不在本文件复制（三处写死必漂）：**口径与数字的唯一登记处是 `docs/ISSUES.md` H36，逐源明细在 `docs/eval/2026-09-24-source-diagnosis.md`**。
结论层面只需要记住四件事：
1. 启用源里**近 14 天真正有产出的只占七成上下**，其余分四种不同的病（从未采到 / 有行但没发布日期 / 停更两周 / 停更过三月），不是一类东西；
2. 最刺眼的一类形状是**产出封顶在十来篇、却仍在全额排队**的那批——它们在反复被抓但拿不到新条目；
3. 后台三个"源数量"各数各的，**同屏必被读成矛盾**（差值是热榜类与人工关闭的，不是丢数据）；
4. 集中度很高：**头部几十个源吃掉一半以上的未读**，热榜类又单独占一大块。

**为什么明确写成"不处置"**：源的情况多种多样（死源、慢源、URL 变更、feed 缺日期、被去重挡住），
一刀切的自动停用会把"暂时没轮到"错杀成"没用"；而且这是后台重构的一部分，要连着界面一起改。
底稿里同时写了一句偏差声明：**"零未读"的源不许直接当死源**（零未读也可能是"你还没读过"而不是"它没内容"）。

### 1.6 贝叶斯/TF-IDF 那套标签实验：把"干掉的是垃圾还是我们需要的"量化完了
你的判据是"它砍掉的是不是我们想要的文章"。所以主判据不是准确率，而是**误砍率**（你标过"留"却被砍）。
结论分两层：
- **信号是真的**：三种零额度方法（朴素贝叶斯 / 互补 NB / TF-IDF 质心）区分"你想读 vs 可删"的能力明显高于
  两个对照（单看文章长度、随机），且置信区间不重叠 ⇒ 它不是"穿了统计外衣的长度规则"。
- **但它替代不了模型初筛**：一旦把误砍约束在 3% 以内，它最多只能砍掉候选池的 **10%**；
  若用它砍一半，会连带干掉你读过的 **26~28%**。三种方法之间**统计上分不出好坏** ⇒ "选哪个模型"是伪问题。
- **可采用的形态只有一个**：放在现有形态规则**之后的"底部一小段"兜底排序**——把最像垃圾的那一小撮在花钱送模型之前先剔掉。

顺带抓出一个自家实现的**反号 bug**（互补 NB 取错了方向），它让此前那句"NB 家族不可信"只剩下的一半。

### 1.7 什么在大量读 Turso：新库 170 MB 的账，和真正该动的那一刀
- 全库正文约 **521M 字符**，其中 **96% 集中在正文这一列**。
- **90 天归档腾不出多少**：90 天前的正文只占全库 7.8%（30 天前 15%）。真正的原因是**增速**：日均 1,875 篇 × 1.5 万字符 ≈ **28M 字符/天**。
- 所以体积杠杆的排序是：**正文自压（实测压缩比 ≈5.9 倍，不动源、不删行）> 放行清理（待删 235 MB / 40.1%）> 截断长度上限（13.6%）> 砍"腹泻源"（1.6%）**。
  最后一条尤其要说出来：**体积大户不是刷屏源，是"一天不到 3 篇、每篇几万字"的低产长文中文源**，砍源省不了空间。
- 读放大侧：三个界面入口都在付"扫全表"的价——精选栏、正文里搜关键字、早报详情（早报统计表没有索引，一次搬走整列）。
  其中"去掉某个类型转换就能用上索引"这种漂亮说法被独立审查推翻了一半：**排序器只是变小，没消失**，所以不许写成已修好。
- 删除闸把"能删的东西"永久锁在库里：跑到的那一次删了 0 条，因为**转储凭证的人工有效期（48 小时）对上每天一趟的清理**——
  有得删的时候闸早关了，而且挡住时没人出声。另有 453 MB 空闲页（上次批量删留下的洞），不整理不还空间。

### 1.8 读者侧证明"功能是能用的"，而不是"链路一半停摆"
用浏览器实际打开线上早报页对最新一期逐项核对：四张主题卡片与库里存的主题**逐条一致**（标题、视角、条数），
统计口径 500/500/60/46 对得上，没有出现"空壳卡片"，也没有降级标。

### 1.9 把自己此前的一句假话拆掉：测试隔离到底挡不挡住了外网
"跑测试时零真实出口"这句此前是**推断**出来的，装置实际看不见——实测：注入一次调用失败，
请求真的发出去并失败了，而台账记的是 0 行。已把该主张从断言里撤下，换成能自证的装置，并把边界写在文档里：
**当前只对明文 HTTP 目标成立**（加密目标是隧道形式到达桩的，现在的记账漏检）。
